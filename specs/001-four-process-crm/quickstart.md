# Как проверить, что работает

**Фича**: 001-four-process-crm

Сценарии проверки по очередям. Каждый проходится на живой системе руками и
подтверждает конкретные требования спецификации. Автоматические проверки — в
`npm run check`, сквозные — в Playwright.

---

## Перед началом

```bash
npm run check
```

Гейт обязан быть зелёным до и после каждой очереди: tsc → границы client/server →
функции-пропы → правила серверного слоя → `any` → визуальный стандарт → кроны →
build → тесты. Пуш без него блокирует хук.

После каждой миграции — перегенерация типов, иначе `tsc` упадёт на новых колонках:

```bash
npm run db:types
```

## Очередь 1 — направления и тарифы

### 1.1 Миграция не потеряла данные (FR-016, FR-017, US-8)

До миграции запомнить: 15 сделок, 14 объектов, 12 договоров, 30 контактов, 64 лида,
32 проводки. После — проверить, что счётчики те же, и что:

- все 15 сделок имеют направление: 13 `rent_agent`, 1 `sale`, 1 `management`;
- все 15 в терминальной стадии своего направления, ни одна не в `null`;
- список «требуют разбора» пуст — это ожидаемый результат на текущих данных;
- объект с `deal_type = 'management'` виден в разделе управления.

Ожидаемо: **ни одна запись не исчезла и не получила случайного направления**.

### 1.2 Четыре воронки различаются (FR-001, FR-002, SC-003)

Завести по одной работе каждого направления и убедиться, что доска показывает разные
колонки: у `rent_agent` — восемь, у `management` — девять с терминальной
«В обслуживании», у `sale` — одиннадцать с проверкой документов и регистрацией, у
`tenant_search` — семь, где договор второй, а не предпоследний.

Ожидаемо: ни в одной воронке нет стадии, которая в этом направлении не наступает.

### 1.3 Предусловие блокирует переход (FR-003, US-4)

На работе направления `tenant_search` попытаться перевести стадию с «Договор на
подбор» на «Поиск вариантов», не подписав договор.

Ожидаемо: переход **не происходит**, сообщение называет причину — не подписан договор
на подбор. Не «ошибка валидации», а именно это.

### 1.4 Чек-лист держит стадию (FR-004)

На стадии «Подготовка и реклама» оставить незакрытым обязательный пункт «загружены
фотографии» и попытаться уйти дальше.

Ожидаемо: отказ с перечислением незакрытых пунктов.

### 1.5 Тариф фиксируется в договоре (FR-005, FR-007, US-5)

1. Завести договор с тарифом «Управление», ставка 10.
2. Изменить ставку тарифа в справочнике на 12.
3. Открыть заключённый договор.

Ожидаемо: **в договоре осталось 10**. Новый договор берёт 12.

### 1.6 Комиссия считается по тарифу (FR-009, SC-004)

Довести работу `rent_agent` до заселения при сумме сделки 50 000 ₽ и тарифе «Агент».

Ожидаемо: начислено 12 500 ₽ (25%). Сверить с ручным расчётом.

### 1.7 Первая сделка бесплатно (FR-010)

Довести до заселения первую сделку с новым собственником.

Ожидаемо: комиссия 0, и в карточке написано, что обнулена по правилу первой сделки —
а не просто пустое поле.

## Очередь 2 — управление

### 2.1 Приёмка не закрывается без показаний (FR-020)

Попытаться закрыть акт приёма, не внеся показание по активному счётчику.

Ожидаемо: отказ, в котором названо, по какому именно счётчику не хватает показания.
После внесения — акт закрывается, обслуживание переходит в `active`.

### 2.2 Аномалии показаний видны (FR-022)

Внести показание меньше предыдущего; затем внести показание после разрыва в два месяца.

Ожидаемо: первое отклонено или требует пометки «замена счётчика», второе принято, но
помечено как разрыв.

### 2.3 Взаиморасчёт при схеме «процент» (FR-029, FR-030, SC-011)

Объект со ставкой 10%. Провести: поступление 50 000 ₽, расход на клининг 3 000 ₽ за
счёт собственника, выплату собственнику 42 000 ₽.

Ожидаемо: вознаграждение 5 000 ₽, сальдо 50 000 − 5 000 − 3 000 − 42 000 = **0**.
Сходится до рубля.

### 2.4 Взаиморасчёт при схеме «фикс» (FR-030, FR-036, SC-012)

Объект с фиксированной выплатой 40 000 ₽ в месяц. Провести месяц с поступлением
50 000 ₽ и месяц простоя без поступлений.

Ожидаемо:
- первый месяц: обязательство 40 000, доход агентства +10 000;
- второй месяц: обязательство 40 000 **возникло всё равно**, доход −40 000;
- накопленный итог по объекту показан как убыток 30 000 ₽.

Это и есть проверка, что риск простоя переехал на агентство.

### 2.5 Лимит мелкого ремонта (FR-027)

При тарифе «Управление» (лимит 5 000) завести ремонт на 7 000 за счёт агентства.

Ожидаемо: предупреждение о превышении на 2 000 и требование либо снизить, либо
перевести превышение на собственника. Молча провести нельзя.

### 2.6 Отчёты различаются по схемам (FR-033)

Сформировать месячный отчёт по объекту со схемой `percent` и по объекту со схемой
`fixed`.

Ожидаемо: в первом видно удержание агентства; во втором — обязательство и факт
выплаты, **без раскрытия дохода агентства**.

### 2.7 Смена арендатора не рвёт историю (FR-035)

Завершить договор найма и завести новый по тому же объекту.

Ожидаемо: обслуживание не прерывается, оба арендатора видны в истории со своими
периодами, сальдо продолжается сквозным.

### 2.8 Регламент не плодит дублей (Р-4)

Прогнать ежедневный крон дважды за один день.

Ожидаемо: регламентные задачи созданы **один раз**. Уникальный индекс по
`(engagement_id, regulation_code, due_date)` держит.

## Очередь 3 — кабинеты и заявки

### 3.1 Вход по коду (FR-038, FR-047)

Запросить код на номер собственника, ввести. Затем: запросить код на номер, которого
нет в базе.

Ожидаемо: ответ на запрос кода **одинаков** в обоих случаях — иначе форма входа
работает как проверка «сотрудничает ли этот человек с агентством». Пять неверных
попыток гасят код.

### 3.2 Собственник видит только своё (FR-036, FR-046, SC-010)

Войти собственником одного объекта и подставить в адрес идентификатор чужого объекта.

Ожидаемо: **404**, неотличимый от несуществующего объекта. Перебором нельзя выяснить,
какие объекты есть.

### 3.3 Отзыв доступа мгновенный (FR-039)

Открыть кабинет, затем отозвать доступ в CRM и обновить страницу.

Ожидаемо: доступ закрыт немедленно, не по истечении сессии.

### 3.4 Показания от арендатора (FR-042)

Внести показание из кабинета арендатора.

Ожидаемо: показание в истории объекта с пометкой источника `tenant`, регламентная
задача на снятие показаний за период закрыта.

### 3.5 Заявка доходит без пересказа (FR-043, FR-044, SC-009)

Оставить заявку на сантехника из кабинета.

Ожидаемо: заявка в CRM с объектом, категорией и описанием; порождена задача
ответственному; арендатор видит статус. Ни одного ручного действия между подачей и
появлением в CRM.

### 3.6 Расход по заявке доходит до отчёта (FR-045)

Закрыть заявку с расходом 3 000 ₽ за счёт собственника.

Ожидаемо: расход в месячном отчёте собственнику и во взаиморасчёте, с указанием, за
чей счёт.

## Сквозные проверки Playwright

Доступы для прогона — в `.env.e2e`.

```bash
npm run test:e2e
```

Минимальный набор, который должен появиться вместе с очередями:

| Сценарий | Очередь |
|---|---|
| Работа `rent_agent` от заведения до комиссии | 1 |
| Блокировка перехода без договора в `tenant_search` | 1 |
| Приёмка объекта и первое показание | 2 |
| Месяц управления по схеме `percent` со сходящимся сальдо | 2 |
| Месяц простоя по схеме `fixed` с отрицательным доходом | 2 |
| Собственник не видит чужой объект | 3 |

стресс-тест по экранам, Playwright, обновлённый README, поднятая версия
(`npm run version:minor` для каждой очереди), формат коммита.
