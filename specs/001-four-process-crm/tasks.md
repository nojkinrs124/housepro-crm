# Tasks: Пересборка CRM вокруг четырёх бизнес-процессов

**Вход**: документы из `specs/001-four-process-crm/`
**Основа**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Тесты**: спецификация не требует TDD. Тестовые задачи включены точечно — там, где
проверка руками ненадёжна: расчёт сальдо по двум схемам, сверка словаря стадий с
CHECK-констрейнтом, разграничение доступа в кабинетах.

## Формат: `[ID] [P?] [Story] Описание`

- **[P]** — можно делать параллельно (разные файлы, нет незакрытых зависимостей)
- **[Story]** — к какой пользовательской истории относится

## Соответствие очередей и фаз

| Очередь | Фазы | Релиз |
|---|---|---|
| 1 — ядро процессов | 1–7 | Один релиз целиком, частичный выкат запрещён |
| 2 — управление | 8–10 | Два релиза: приёмка и счётчики, затем деньги и отчёт |
| 3 — кабинеты | 11–12 | Один релиз |

## Зависимости

```
Phase 1 (конфиг) ─┐
                  ├─► Phase 2 (миграции) ─► Phase 3 (US5 тарифы)
                  │                              │
                  │                              ├─► Phase 4 (US1 аренда) 🎯 MVP
                  │                              ├─► Phase 5 (US2 воронка управления)
                  │                              ├─► Phase 6 (US3 продажа)
                  │                              └─► Phase 7 (US4 подбор) ─► выкат очереди 1
                  │                                                              │
                  └──────────────────────────────────────────────────────────────┤
                                                                                 ▼
                                    Phase 8 (приёмка, счётчики) ─► Phase 9 (деньги) ─► Phase 10 (регламент)
                                                                                                │
                                                                                                ▼
                                                              Phase 11 (кабинеты) ─► Phase 12 (заявки) ─► Phase 13
```

**Жёсткие зависимости**:

- Phase 2 блокирует всё: без миграции направлений нет ни одной воронки.
- Phase 3 (тарифы) идёт перед Phase 4 и 5: без тарифа не посчитать комиссию и не выбрать схему расчёта.
- Phase 9 (деньги) требует Phase 8: сальдо считается по объекту в управлении, которого до приёмки нет.
- Phase 11 требует Phase 9: отчёт и взаиморасчёт — то, ради чего собственник заходит в кабинет.

**Что можно делать параллельно**:

- Phases 4, 5, 6, 7 после закрытия Phase 3 — четыре направления не пересекаются нигде, кроме общего конфига.
- Внутри Phase 8: счётчики (T057–T059) и приёмка (T055–T056) — разные файлы.
- Внутри Phase 13: пять сценариев Playwright независимы.

## Стратегия реализации

**MVP** — Phases 1–4: направления, миграция данных, тарифы и полностью работающая аренда по тарифу «Агент». Это уже даёт то, чего сегодня нет: путь от объявления до комиссии внутри системы, с посчитанной комиссией.

**Очередь 1 целиком** — Phases 1–7. Выкатывается одним релизом: направление без своей воронки хуже текущего состояния, поэтому частичный выкат запрещён (принцип VII конституции).

**Дальше по одной очереди**, каждая со своим релизом, зелёным `npm run check` и поднятой версией.

**Правило по ходу**: перед каждым выкатом — процедура из skill `housepro-release`. Перед каждой миграцией — `apply_migration`, не `execute_sql`. После каждой миграции — перегенерация типов, иначе `tsc` упадёт на новых колонках, и это выяснится на сборке, а не на правке.
