# Implementation Plan: Пересборка CRM вокруг четырёх бизнес-процессов

**Branch**: `001-four-process-crm` | **Date**: 2026-09-03 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `specs/001-four-process-crm/spec.md`

## Summary

Четыре направления работы вместо одной универсальной воронки, тарифы как справочник,
две схемы расчёта с собственником, непрерывное управление объектом и личные кабинеты
собственника и арендатора.

Технический подход — **переиспользование, а не переписывание**. Ключевые решения:

1. **`deals.deal_type` становится направлением.** Не новая колонка рядом со старой, а
   переосмысление существующей: значения переименовываются миграцией (15 строк),
   CHECK-констрейнт переписывается под четыре направления. Весь код, читающий
   `deal_type`, продолжает работать — меняются значения и словарь лейблов.
2. **Стадии — расширение `deals.status`.** CHECK принимает объединение стадий всех
   направлений; принадлежность стадии направлению проверяется в Server Action по
   конфигу, а не составным констрейнтом в базе.
3. **Арендатор — это договор найма, а не новая сущность.** История арендаторов
   объекта = история договоров `rent_apartment` по нему. Новая таблица не заводится.
4. **Регламент управления — это задачи.** Регулярные события генерируются в
   существующую таблицу `tasks`, которая уже связана с объектом, имеет срок, статус и
   отображается в календаре и напоминаниях.
5. **Взаиморасчёт — на `accounting_transactions`.** Таблица уже несёт `property_id`,
   `contract_id`, `contact_id`, `type`, `status`, `period_start/period_end` и
   категории. Добавляются две колонки и категории, сальдо считается запросом.
6. **Счётчикам схема не нужна.** `utility_meters` и `meter_readings` уже существуют с
   правильной структурой и пусты. Нужен только интерфейс и отчёты.

Новых таблиц четыре: `service_plans`, `management_engagements`, `service_requests`,
`portal_access`. Всё остальное — расширение существующего.

## Technical Context

**Language/Version**: TypeScript 7, Next.js 16 (App Router), React 19

**Primary Dependencies**: Supabase (Postgres + Auth + Storage), react-hook-form + zod,
docxtemplater + pizzip, pdf-lib, recharts, sonner, framer-motion, lucide-react,
Upstash Redis (rate limit), Tailwind v4 через postcss

**Storage**: Postgres в Supabase. 48 таблиц, RLS на всех, изоляция через
`get_user_org_id()`

**Testing**: vitest (юнит) + Playwright (E2E), гейт `npm run check`

**Target Platform**: Vercel (тариф Hobby — ограничение на частоту кронов),
прод `housepro24.vercel.app`

**Project Type**: Web-приложение с серверным рендерингом; CRM-часть под авторизацией,
публичный сайт и личные кабинеты — отдельные сегменты

**Performance Goals**: списки и карточки открываются без заметной задержки на объёме
до нескольких сотен объектов и нескольких тысяч операций; расчёт сальдо и месячного
отчёта — одним запросом на объект, без выборок в цикле

**Constraints**: изменение схемы только через `apply_migration`; `DROP TABLE`,
`TRUNCATE`, `DROP COLUMN` заблокированы хуком — legacy-колонки остаются на месте;
кроны ограничены тарифом Hobby; ESLint в проекте не работает (TS 7 не поддерживается
`typescript-eslint`), качество держат `npm run check` и собственные линтеры

**Scale/Scope**: один сотрудник (самозанятый), одна организация, 14 объектов,
30 контактов, 12 договоров, 15 сделок, 64 лида. Мультиарендность в схеме уже есть и
сохраняется. Объём работы — три очереди, около 90 существующих страниц затрагиваются
частично, новых экранов порядка 20

## Constitution Check

*Проверено против `.specify/memory/constitution.md` до Phase 0 и повторно после Phase 1.*

| Принцип | Как соблюдается |
|---|---|
| **I. Граница Server/Client** | Новые экраны — серверные страницы, вся интерактивность (Kanban направлений, форма показаний, конструктор регламента, форма заявки) выносится в отдельные файлы с `'use client'`. Конфиг направлений `directions.ts` — без `'use client'`, по образцу `deal-stages.ts` и `lead-statuses.ts`, потому что его читают и серверные страницы, и клиентские компоненты. Функции пропами не передаются: настройки стадий уезжают в клиент сериализуемыми объектами. |
| **II. Схема только миграцией** | 4 новые таблицы и 6 изменений существующих — все через `apply_migration`. Каждая новая таблица несёт `organization_id` и RLS с `get_user_org_id()`. `DROP COLUMN` не используется: legacy-колонки `deals.client_id`/`owner_id` остаются. Переписывание CHECK — через `DROP CONSTRAINT` + `ADD CONSTRAINT`, это разрешено (образец — `20260902_sync_leads_status_check_with_code.sql`). Типы перегенерируются после каждой миграции. |
| **III. Типы вместо `any`** | Новый код без `any`; доменные union'ы направлений, стадий и схем расчёта — в `src/types/database.ts` поверх сгенерированной схемы. Ратчет `check:any` не растёт. |
| **IV. Визуальный стандарт** | Все экраны на существующих примитивах `.hp-block`, `.hp-badge`, `.hp-input`; доска направлений использует уже готовый `DealsKanban` и `STAGE_COLORS`; новых цветов и радиусов не вводится. |
| **V. Server Action как точка записи** | Каждая мутация по шаблону: `auth.getUser()` → `requireOrgId()` → rate limit → zod → запрос → `revalidatePath`. Действия кабинета — отдельный слой с собственной проверкой владения, см. отступление ниже. |
| **VI. Зелёная проверка и версия** | Каждая очередь выкатывается отдельным коммитом с поднятой версией и зелёным `npm run check`; порядок — skill `housepro-release`. |
| **VII. Без заглушек** | Очередь считается сделанной, когда работает целиком. Очередь 1 не выкатывается частично: направление без своей воронки хуже, чем текущее состояние. |

### Отступление, требующее обоснования

| Нарушение | Зачем нужно | Почему отвергнута простая альтернатива |
|---|---|---|
| Личные кабинеты обслуживаются не через `get_user_org_id()`, а через собственную проверку владения по `portal_access` | Собственник и арендатор — не сотрудники организации. У них нет записи в `organization_members`, и `get_user_org_id()` для них возвращает пусто: под действующими политиками они не увидят ничего. Нужен второй, независимый контур доступа | Завести их сотрудниками организации отвергнуто: это дало бы им доступ ко всей организации и превратило бы RLS в решето. Отдельный контур: доступ выдаётся только на конкретный объект и договор, проверка идёт по таблице `portal_access` с явной связью «контакт → объект → роль», срок жизни и отзыв обязательны (FR-039, FR-043, FR-046) |

Отступление ограничено очередью 3 и не затрагивает CRM-часть: изоляция по
организации там работает как прежде.

`(portal)` — рядом с существующими `(dashboard)`, `(site)`, `(auth)`, — потому что у
них другой контур доступа и другой макет. Новых верхнеуровневых каталогов и второго
приложения не заводится.

## Очерёдность и границы выката

| Очередь | Требования | Что выкатывается | Условие |
|---|---|---|---|
| 1 | FR-001 — FR-018 | Направления, четыре воронки, тарифы, миграция данных, перегруппировка меню | Выкатывается целиком одним релизом. Частичный выкат запрещён: направление без своей воронки хуже текущего состояния |
| 2 | FR-019 — FR-037 | Приёмка, счётчики, регламент, расходы, взаиморасчёт, отчёт, простой | Требует очереди 1. Внутри делится на два релиза: приёмка и счётчики — первым, деньги и отчёт — вторым |
| 3 | FR-038 — FR-047 | Кабинеты собственника и арендатора, заявки | Требует очередей 1 и 2 (отчёт и взаиморасчёт — то, ради чего собственник заходит) |

## Complexity Tracking

Единственное отступление от конституции — второй контур доступа для личных кабинетов
— описано выше в разделе «Отступление, требующее обоснования» и ограничено очередью 3.

Прочих отступлений нет: новых зависимостей не вводится, библиотеки компонентов не
появляется, схема расширяется без удаления данных.
