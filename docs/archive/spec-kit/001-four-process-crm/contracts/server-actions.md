# Контракт: Server Actions

**Фича**: 001-four-process-crm

Все действия следуют шаблону из `CLAUDE.md`: `auth.getUser()` → `requireOrgId()` →
rate limit → zod → запрос → `revalidatePath`. Возврат — `{ error: string }` при отказе,
`redirect` или `{ ok: true, … }` при успехе. Приведены сигнатуры и правила отказа;
тела — в реализации.

---

## Направления и стадии — `src/features/directions`

### `moveStageAction(formData)`

Перевод работы на другую стадию.

| Вход | |
|---|---|
| `dealId` | uuid, обязателен |
| `toStage` | код стадии |
| `comment` | текст, необязателен |

**Отказы**:
- стадия не принадлежит направлению работы → `Стадия «{X}» не применяется в направлении «{Y}»`;
- не выполнено предусловие → текст называет, чего именно не хватает: `Нельзя перейти к поиску вариантов: не подписан договор на подбор`;
- не закрыты обязательные пункты чек-листа текущей стадии → перечисляет незакрытые;
- работа в терминальной стадии → `Работа завершена, стадию сменить нельзя`.

**Побочные эффекты**: запись в историю стадий (дата, автор, комментарий);
`revalidatePath('/deals')` и карточки.

## Тарифы — `src/features/plans`

### `createPlanAction(formData)` · `updatePlanAction(formData)`

| Вход | |
|---|---|
| `code`, `title` | обязательны, `code` уникален в организации |
| `charge_type` | `deal_percent` · `monthly_percent` · `owner_fixed` · `flat_fee` · `negotiated` |
| `rate` | обязателен для `*_percent` и `flat_fee`; запрещён для `negotiated` |
| `repair_limit`, `obligations`, `directions`, `is_active` | |

**Отказы**: дублирующийся `code`; `rate` вне 0–100 для процентных типов; попытка
деактивировать тариф, на который ссылается действующий договор → предупреждение, что
действующие договоры сохранят свою ставку, и подтверждение.

**Инвариант**: изменение `rate` **не трогает** `contracts.plan_rate` уже заключённых
договоров (FR-007).

## Управление — `src/features/management`

### `startEngagementAction(formData)`

Заведение объекта в управлении после подписания договора управления.

| Вход | |
|---|---|
| `propertyId`, `ownerContactId`, `contractId`, `planId` | обязательны |
| `settlementScheme` | `percent` \| `fixed` |
| `rate` | обязателен при `percent` |
| `ownerFixedAmount`, `ownerPayoutDay` | обязательны при `fixed` |
| `startedAt` | дата |

**Отказы**: договор не типа `property_management` или не подписан; по объекту уже есть
действующее обслуживание; схема и её параметры не согласованы.

**Побочные эффекты**: создаётся `management_engagements` в статусе `onboarding` и
пустой `property_handovers`; сделка переводится в стадию `handover`.

### `completeHandoverAction(formData)`

Закрытие акта приёма.

**Отказы** (FR-020) — называют недостающее поимённо:
- нет показания по активному счётчику `{название}`;
- опись имущества пуста;
- не указано число переданных ключей.

**Побочные эффекты**: `completed_at`, обслуживание → `active`, генерация регламентных
задач на ближайший период.

### `addReadingAction(formData)`

| Вход | `meterId`, `readingDate`, `value`, `note`, `source` (`manager` \| `tenant`) |
|---|---|

**Отказы**: показание меньше предыдущего без пометки «замена счётчика»; дата в будущем;
показание за уже закрытый период отчёта.

**Побочные эффекты**: расчёт `consumption` и `amount`; закрытие регламентной задачи
`meter_reading` за период.

### `registerTenantPaymentAction(formData)`

Поступление от арендатора по объекту в управлении.

| Вход | `engagementId`, `amount`, `date`, `periodStart`, `periodEnd`, `paymentMethod` |
|---|---|

**Побочные эффекты по схеме расчёта**:
- `percent`: создаётся доход категории `tenant_payment` и доход `agency_fee` на
  `rate` % от суммы; остаток формирует обязательство перед собственником;
- `fixed`: создаётся доход `tenant_payment`; обязательство перед собственником уже
  создано календарём и не зависит от этого поступления (FR-030).

### `payOwnerAction(formData)`

| Вход | `engagementId`, `amount`, `date`, `periodStart`, `periodEnd` |
|---|---|

**Отказы**: сумма превышает текущее сальдо более чем на копейку без явной пометки
«аванс»; период пересекается с уже закрытым.

**Побочные эффекты**: расход категории `owner_payout`, уменьшение сальдо.

### `addExpenseAction(formData)`

| Вход | `engagementId`, `categoryCode`, `amount`, `date`, `borneBy` (`agency` \| `owner`), `description` |
|---|---|

**Правило лимита** (FR-027): при `categoryCode = 'repair_minor'` и `borneBy = 'agency'`,
если сумма расходов этой категории за календарный месяц превысит
`engagement.repair_limit`, действие возвращает предупреждение с суммой превышения и
требует либо снизить сумму, либо перевести превышение на `borneBy = 'owner'`.

### `buildMonthlyReportAction(formData)`

| Вход | `engagementId`, `year`, `month` |
|---|---|

Собирает отчёт **в составе, соответствующем схеме** (FR-033):
- `percent` — поступления, удержание агентства, расходы по категориям, выплачено,
  к выплате, сальдо;
- `fixed` — обязательство за период, факт выплаты, расходы за счёт собственника;
  доход агентства **не раскрывается**.

**Отказ**: период не закрыт — есть операции в статусе `planned` внутри периода.

## Общие правила отказов

1. Сообщение об ошибке называет **что именно** не так и **что сделать**, а не
   «Ошибка валидации». Это прямое требование FR-003.
2. Ни одно действие не выполняется частично: если побочный эффект не удался, основная
   запись откатывается.
3. Rate limit применяется ко всем создающим действиям, как в существующем коде.
