# Контракт: личные кабинеты

**Фича**: 001-four-process-crm · **Очередь 3**

Кабинеты живут в сегменте маршрутов `src/app/(portal)`. Контур доступа отдельный от
CRM: не `get_user_org_id()`, а проверка владения по `portal_access`. Обоснование — в
[plan.md](../plan.md#отступление-требующее-обоснования).

---

## Вход

### `POST /api/portal/otp/request`

| Вход | `phone` |
|---|---|
| Ответ | `{ ok: true, channel: 'telegram' \| 'sms', maskedTarget: '+7 ··· ·· 89' }` |

**Правила**:
- ответ **одинаков** для существующего и несуществующего номера — иначе форма входа
  превращается в способ проверять, работает ли человек с агентством;
- код генерируется случайно, хранится **только хешем**, живёт минуты;
- канал выбирается так: Telegram, если у контакта заполнен `telegram` и он писал боту;
  иначе SMS, если провайдер настроен; иначе отказ с текстом о том, что нужно
  обратиться к менеджеру;
- ограничение частоты: не чаще одного запроса в минуту на номер и не более пяти в час
  (FR-047), поверх существующего Upstash Redis.

### `POST /api/portal/otp/verify`

| Вход | `phone`, `code` |
|---|---|
| Ответ | `Set-Cookie` с подписанной сессией; `{ ok: true, roles: ['owner' \| 'tenant'] }` |

**Правила**: не более пяти попыток на код; после исчерпания код погашается;
`consumed_at` не даёт использовать код дважды; срок жизни сессии короткий, отзыв
возможен (FR-043).

Если у одного номера есть и роль собственника, и роль арендатора, ответ возвращает обе
— кабинет показывает переключатель.

---

## Кабинет собственника

Все маршруты требуют действующей сессии с ролью `owner` и отдают **только** объекты, на
которые есть неотозванная запись в `portal_access`.

| Маршрут | Отдаёт |
|---|---|
| `GET /owner` | Список своих объектов: адрес, статус, текущий арендатор, срок договора |
| `GET /owner/property/[id]` | Карточка: арендатор и срок, показания счётчиков, документы |
| `GET /owner/property/[id]/reports` | Список месячных отчётов |
| `GET /owner/property/[id]/reports/[period]` | Отчёт за период — **в составе по схеме договора** (FR-033) |
| `GET /owner/property/[id]/payments` | История платежей и выплат |

**Что собственник не видит никогда**: другие объекты, персональные данные арендатора
сверх имени и срока договора, внутренние задачи и комментарии, а при схеме `fixed` —
доход агентства.

---

## Кабинет арендатора

Требует сессии с ролью `tenant`; объём ограничен объектом действующего договора найма.

| Маршрут | Отдаёт |
|---|---|
| `GET /tenant` | Свой объект, срок договора, ближайшая дата платежа |
| `GET /tenant/payments` | История своих платежей и предстоящие начисления |
| `GET /tenant/meters` | Свои счётчики и история показаний |
| `POST /tenant/meters/reading` | Внесение показания — пишется с `source = 'tenant'` (FR-042) |
| `GET /tenant/requests` | Свои заявки и их статусы |
| `POST /tenant/requests` | Создание заявки: категория, описание, фотографии |

**Что арендатор не видит никогда**: сумму вознаграждения агентства, расчёты с
собственником, персональные данные собственника, другие объекты.

---

## Правила, общие для обоих кабинетов

1. **Каждый запрос проверяет владение заново.** Идентификатор объекта из адреса
   никогда не считается доверенным: сначала проверяется, что у сессии есть
   неотозванный `portal_access` на этот объект, и только потом читаются данные
   (FR-046).
2. **Отозванный доступ действует немедленно.** Прекращение договора закрывает кабинет
   без ожидания истечения сессии.
3. **Ошибка доступа неотличима от отсутствия объекта** — и то и другое отдаёт 404.
   Иначе перебором идентификаторов можно установить, какие объекты существуют.
4. **Загрузка фотографий** идёт через существующий модуль файлов и Storage, с
   ограничением на размер и тип; посторонние типы отклоняются на сервере, а не только
   в форме.
