# Сквозной проход по CRM — инструкция для агента-тестировщика

Цель: пройти CRM **глазами нанятого риелтора** через реальный браузер — от звонка
клиента до закрытой сделки и денег в кассе — по **всем четырём направлениям**,
и зафиксировать каждое место, где цепочка рвётся, логика врёт или человек не
понимает, что делать дальше.

Это не smoke (он в `e2e/smoke/` и проверяет «не упало»). Здесь проверяется
**смысл**: правильно ли система ведёт по воронке, сходятся ли данные между
модулями, не даёт ли она сделать невозможное и не мешает ли сделать нужное.

Запуск — командой `/walkthrough` (см. `.claude/commands/walkthrough.md`).
Исполнитель шагов — агент `crm-walkthrough` (`.claude/agents/crm-walkthrough.md`).

---

## 0. Окружение и правила безопасности

- **Только изолированный Supabase.** Локальный стек в Docker + production-сборка
  CRM на `http://localhost:3100`. Подъём: `npm run walkthrough:up`.
  Прод-ref `zwclvcswvhjeqwxrkbte` и любой `*.supabase.co` — стоп.
- **Вход** — учётка-фикстура смоука из `.env.e2e.branch`
  (`E2E_TEST_EMAIL` / `E2E_TEST_PASSWORD`). Это локальная тестовая запись, не
  секрет владельца. Настоящие учётки в браузер не вводить никогда.
- `.env.local`, `.env.e2e` — файлы прода: не читать, не печатать, не менять.
- **Ничего не чинить по ходу.** Проход — только наблюдение и отчёт. Исправления —
  отдельным решением владельца после отчёта.
- Все создаваемые записи именовать с префиксом `__wt__` (например
  `__wt__ Иванов Пётр`), чтобы их можно было отличить и вычистить.
- Режим `prod` (только чтение боевого `housepro24.vercel.app`): владелец сам
  входит в браузере; агент **только смотрит и читает** — ни одной формы, ни
  одной кнопки действия. Используется, чтобы сверить вид реальных данных с тем,
  что показала локальная база.

## 1. Что считается дефектом и как оценивать

| Класс | Что это | Пример |
|---|---|---|
| **Блокер** | Сценарий невозможно довести до конца | Кнопки «дальше» нет; форма не сохраняется; страница 404/500 |
| **Логика** | Система позволяет невозможное или запрещает нужное; данные между модулями расходятся | Сделку можно завершить без договора; конвертация лида создаёт дубль контакта; сумма в аналитике ≠ сумме операций |
| **Разрыв** | Данные не переносятся между шагами, приходится вводить повторно или искать руками | Из показа не попасть в сделку; договор не знает объект сделки |
| **UX** | Понятно, но долго/неочевидно/лишний шаг | 5 кликов вместо 3; подтверждение обратимого действия |
| **Текст** | Жаргон, код вместо подписи, ошибка без объяснения | `sourcing` вместо «Поиск и контакт»; «Не получилось сохранить» без причины |

На **каждом** экране дополнительно прогоняются восемь правил интерфейса из
`CLAUDE.md` (≤3 клика, одна главная кнопка, ≤6 полей, единый скелет, нет
пустых экранов, человеческий язык, подтверждать только необратимое, одно
действие — один способ).

**Формат записи дефекта** (одна строка в таблице отчёта):

```
| RA-5.3 | Логика | Переход «Показы → Проверка» прошёл без отметки заинтересованного клиента | Ожидал блокировку с текстом из preconditions.ts | /deals/<id>, тост «Стадия: Проверка и договор найма» | src/features/directions/services/transitions.ts: для interested_client нет DATA_CHECK |
```

Колонки: ID шага · класс · что произошло · что ожидалось · где (URL + цитата
с экрана) · подсказка, где в коде (если очевидно; иначе пусто).

## 2. Как читать шаги

Каждый шаг: **Действие → Ожидание → Проверить**. «Проверить» — это инварианты,
которые обязаны выполняться; их нарушение = дефект класса «Логика».

Кнопки и поля названы так, как они подписаны в интерфейсе. Если подписи нет
на экране — это уже дефект (Текст/UX), запиши и найди элемент через `find`.

Правило трёх кликов считать от `/dashboard`.

## 6. Направление RA — Аренда, тариф «Агент»

Стадии по коду (`src/features/directions/config/directions.ts`):
`sourcing → meeting → agency_contract → preparation → showings → tenant_check → move_in → completed`, плюс `cancelled`.

Для каждой стадии на карточке сделки есть **чек-лист** (обязательные пункты)
и **предусловия** следующей стадии. Правила проверки на каждой стадии:

- (а) Попытка перейти дальше **с незакрытым обязательным пунктом** → блокировка
  с перечислением пунктов. Прошло — Логика.
- (б) Попытка перейти дальше с закрытым чек-листом, но **без данных**
  (нет договора / тарифа / фото / публикации / дохода) → блокировка с текстом из
  `preconditions.ts`. Прошло — Логика. Особо: часть предусловий в коде
  объявлена, но не проверяется по данным (`meeting_scheduled`, `meeting_done`,
  `interested_client`, `cancel_reason`, `valuation_done`, `docs_checked`,
  `buyer_found`, `settlement_closed`, `commission_fixed`, `collection_built`,
  `collection_sent`, `property_chosen`, `handover_completed`,
  `engagement_started`). Зафиксируй **каждую**, которую удалось обойти.
- (в) Переход **назад** разрешён без условий — проверить, что чек-лист прошлой
  стадии не потерялся.
- (г) Прыжок через стадию (например, из «Встреча» сразу в «Показы») —
  должен ли быть разрешён? Запиши поведение.

| ID | Действие | Ожидание | Проверить |
|---|---|---|---|
| RA-0 | С карточки Сидорова «Новая сделка»: направление «Аренда, тариф „Агент“», объект Ленина 15, источник | Карточка сделки, стадия «Поиск и контакт», номер `СД-N` | Собственник = Сидоров; объект кликабелен; главная кнопка одна |
| RA-1 | Стадия «Поиск и контакт»: закрыть чек-лист (источник, дозвон) | Галочки сохраняются после перезагрузки | Правила (а) |
| RA-2 | «Встреча»: без назначенной встречи перейти | ? | `meeting_scheduled` — проверь (б). Как вообще назначить встречу — есть ли путь? Если только через задачу/показ — Разрыв |
| RA-3 | «Договор с собственником»: чек-лист; затем «Оформить» (`/deals/<id>/complete`) | Создан договор «Агентский договор с собственником», задача на подписание, предложен тариф | Тип договора выбран по направлению; договор виден на карточке сделки; тариф из SET-2 |
