# Инструкция: сквозной UI-тест HousePro CRM «глазами пользователя»

Цель — пройти CRM так, как её проходит живой сотрудник агентства: каждый путь,
каждая кнопка, каждая форма, с правильными, пустыми и кривыми данными. Найти
всё, что ломается, теряет данные, сбивает с толку или выглядит криво.

Зелёный `npm run check` и «страница открылась» — НЕ доказательство. Доказательство —
пройденный руками сценарий + перечитанное состояние (карточка после перезагрузки
или запись в БД).

## 0. Среда (обязательно)

| Что | Значение |
|---|---|
| CRM | `http://192.168.3.14:3100` (только этот хост — с `localhost`/`127.0.0.1` гидрация ломается) |
| База | локальный Supabase в Docker (`supabase_db_Claude`), НЕ прод |
| Пользователь | `smoke@housepro.local`, пароль — `E2E_TEST_PASSWORD` в `.env.e2e.branch` (в чат/отчёт не писать) |
| Хелпер входа | `~/.hermes/cache/scratch/qa/crm_login.py` → `crm_login('/deals')`, `set_value(sel, v)`, `form_dump()`, `errors_on_page()` |
| SQL для проверки | `docker exec supabase_db_Claude psql -U postgres -tAc "select ..."` — ТОЛЬКО select |
| Лог сервера | `~/.hermes/cache/scratch/qa-dev.log` (ошибки сервера, 500, `[db]`) |

Запреты:
- Прод (`housepro24.ru`) не открывать вообще.
- Код репозитория не менять. Только тестируем и пишем отчёт.
- Каждой создаваемой записи — префикс `__smoke__ <агент>` в названии/имени
  (пример: `__smoke__ A Иванов Пётр`), чтобы её можно было найти и удалить.
- Не удалять чужие записи (без своего префикса).
- Интеграции (Telegram, Авито, почта) в стенде отключены — отправка письма должна
  уйти в режим `log`, это ок; если что-то реально пытается выйти в интернет — это находка.

Как работать с браузером (грабли, на которые уже наступали):
- Своё имя сессии браузера (`qa-a`, `qa-b`…) во всех вызовах.
- После навигации `cdp('Emulation.setFocusEmulationEnabled', enabled=True)` — иначе вкладка «спит».
- Даты и select'ы — только через `set_value()` (посимвольный ввод даты даёт мусор).
  Для select сначала прочитай `[...sel.options].map(o=>o.value)` и ставь точное value.
- Перед кликом по кнопке: найди по ТОЧНОМУ тексту (`trim()===`), `scrollIntoView`,
  потом клик. В шапке есть глобальная «Создать» — не путай с сабмитом формы.
- После сохранения (server action) — заново открой URL и перечитай; текущий DOM может быть устаревшим.
- Редирект на `/login` = истёк токен. Просто снова `crm_login(path)`.
- Первое открытие страницы в dev-режиме компилируется до 30–60 с — это не баг.
  Баг — если после прогрева страница стабильно грузится > 5 с.
- Кликом «по-человечески» считается клик по видимой кнопке. Если элемент не видно
  без прокрутки до конца страницы / его не найти глазами — это UX-находка.

## 1. Как проверять каждую форму (минимальный набор на любую форму)

Для КАЖДОЙ формы создания/редактирования:

1. **Пустая отправка** — нажать «Сохранить» без данных. Ожидание: понятная ошибка у
   конкретного поля, введённое НЕ сбрасывается.
2. **Счастливый путь** — заполнить всё корректно → сохранить → открыть карточку →
   сравнить КАЖДОЕ поле с тем, что вводили (`form_dump()` до и текст карточки после).
3. **Кривые значения** по одному: отрицательное число, 0, буквы в числе, огромное
   число (1e12), дата окончания раньше даты начала, дата в 1900 и 2100 году, пробелы
   вместо текста, 500 символов, эмодзи, кавычки `"' <b>`.
4. **Ошибка → сохранность ввода.** После ЛЮБОЙ ошибки валидации проверить: остались ли
   все введённые поля (стороны, объект, даты, суммы). Сброс данных = находка P1.
5. **Обязательность.** Может ли сохраниться документ без ключевых данных (договор без
   сторон/дат/суммы)? Если да и это ломает дальше (DOCX, график) — находка.
6. **Редактирование** — открыть «Редактировать», изменить одно поле, сохранить, убедиться,
   что остальные поля не обнулились (особенно select'ы с контактами и даты).
7. **Удаление** — подтверждение есть? что стало со связанными записями?
8. **Двойной клик по «Сохранить»** — не создались ли две записи (проверь SQL count).

## 2. Как проверять каждый экран-список (реестр/канбан)

1. Каждый фильтр по очереди: выставить → посчитать строки на экране → сверить
   с SQL `select count(*) ... where <тот же фильтр>`. Не совпало = баг.
2. Комбинация двух фильтров, сброс фильтров, фильтр + поиск, фильтр после F5 (сохраняется ли в URL).
3. Поиск: по части имени, телефону, номеру, регистру, «ё/е».
4. Сортировка по колонкам (если есть).
5. Пустое состояние: фильтр, по которому ничего нет, — понятный текст, а не пустота.
6. Ширина 1280/1440/1920 (`cdp('Emulation.setDeviceMetricsOverride', width=1280, height=800, deviceScaleFactor=1, mobile=False)`):
   есть ли горизонтальный скролл (`scrollWidth - clientWidth` у контейнера), обрезанный текст.
7. Канбан: видны ли ВСЕ колонки без прокрутки страницы до самого низа; есть ли
   стрелки/кнопки прокрутки; можно ли перетащить карточку; что происходит при переносе
   в недопустимую стадию (понятный отказ?).

## 3. Сквозные сценарии (пути пользователя)

Каждый сценарий — от пустого места до финала. На КАЖДОЙ стадии записывать:
- какие кнопки видны в шапке/карточке сделки (`[...document.querySelectorAll('main button, main a')].map(e=>e.innerText.trim()).filter(Boolean)`);
- уместны ли они на этой стадии (кнопка, которая на этой стадии бессмысленна, или
  отсутствие нужной кнопки — UX-находка);
- чек-лист стадии и понятно ли, что делать дальше;
- что происходит при попытке перескочить стадию.

### S1. Аренда «Агент» (полная воронка)
Лид → контакт собственника → объект → сделка «Аренда, тариф Агент» →
Встреча → **Договор с собственником** (создать агентский договор из сделки: кнопкой
«Договор», через «Оформить» и через «…»→«Договор вручную» — все три пути) →
Подготовка (фото, публикация, тариф) → Показы (показ, результат) → Проверка и
договор найма (договор найма через «Оформить», с залогом и без) → Заселение →
комиссия → Завершена → статус объекта «Сдан».

Обязательные регрессии (жалобы владельца 28.10.2026):
- R1. Договор из сделки на стадии «Договор с собственником»: подставился ли собственник,
  объект, даты начала/окончания? Ничего не сбросилось после создания?
- R2. Агентский договор → «Сформировать документ»: текст договора полный (предмет,
  обязанности, вознаграждение, срок, реквизиты) или пустой бланк с именами?
- R3. Блок «Платежи» и «Сформировать график платежей» в агентском договоре: понятно ли
  что это и зачем; что реально создаётся (SQL `accounting_transactions` по `contract_id`).
- R4. Договор найма через «Оформить»/форму: ошибка «укажите положительное число» —
  на каком поле, при каких данных; сбрасываются ли данные после ошибки.
- R5. Договор найма с ПУСТЫМ залогом, пустыми датами начала/конца, пустыми полями
  «дети/животные», пустой датой акта — создаётся ли (не должен молча создаваться
  неполноценный договор, либо должен явно предупредить).
- R6. Сформированный DOCX: отступы, шрифты, переносы, пустые плейсхолдеры `{...}`,
  «undefined», «null», «NaN», дата в формате ISO, суммы без пробелов-разделителей.
- R7. Канбан сделок: как добраться до правых колонок — нужна ли прокрутка до низа
  страницы к горизонтальному бегунку; есть ли стрелки.
- R8. Кнопки по стадиям: при движении по стадиям появляются нужные и исчезают ненужные?

### S2. Управление
Сделка «Управление» → Встреча → Договор управления (каждая из трёх схем расчёта) →
Приёмка объекта (акт, показания, опись) → Подготовка → Показы → договор найма →
Заселение → «Принять в управление» → В обслуживании → раздел «Управление»:
карточка, финансы, условия, люди, расчёт с собственником (`/settlement`), отчёт
собственнику (`/report`) — сформировать, проверить цифры.

### S3. Продажа и покупка
Сделка «Продажа» → оценка → агентский договор → проверка документов → подготовка →
показы → предварительный договор (аванс/задаток, срок выхода) → основной договор
(купля-продажа) → регистрация → закрытие расчётов → «Продан».

### S4. Подбор для арендатора
Обращение → договор на подбор (без объекта!) → поиск вариантов (подборка из 2–3
объектов) → отправить подборку, открыть публичную ссылку `/c/[token]` → просмотры →
договор найма → завершение.

### S5. Отмена и откат
Отменить сделку с каждой стадии (с причиной и без) → вернуть в работу. Откат стадии
назад. Откат договора «Подписан» → «Черновик»: что с сделкой.

### S6. Договоры напрямую (`/contracts/new`) — все 8 типов
Аренда квартиры, Коммерческая аренда, Купля-продажа, Агентский (собственник),
Агентский (клиент), Агентский с юрлицом, Управление, Субаренда. Для каждого:
форма по §1 → карточка → статусы Черновик→Создан→Подписан→Завершён → «Сформировать
документ» (DOCX) → версии → «Проверить данные для документа» → блок платежей:
разовое начисление и график (с залогом, индексацией, разной периодичностью) →
удалить договор.

### S7. Лиды
Создать лиды в разных статусах; **каждый фильтр** (особенно «Новые» — жалоба: показывает
все лиды) с SQL-сверкой; групповые действия; конвертация в контакт/сделку; карточка.

### S8. Контакты, объекты, показы, подборки
CRUD по §1; дубли контактов (`/contacts/duplicates`); объект: фото, публикация,
счётчики, «Чего не хватает»; показ: назначить, завершить с результатом, календарь показов.

### S9. Задачи, календарь, бухгалтерия, платежи, аналитика
Задача из сделки и отдельно; календарь; операция дохода/расхода; категории;
повторяющиеся; счёт на оплату (`/accounting/invoice/[id]`); импорт выписки;
платежи (`/payments`); аналитика — сверить 2–3 цифры с SQL.

### S10. Настройки, сотрудники, база знаний, поиск, экспорт, личный кабинет
Все страницы `/settings/*` (открыть, сохранить без изменений, изменить одно поле);
шаблоны документов (`/settings/templates`) — есть ли шаблон у каждого типа договора;
сотрудник; статья базы знаний; глобальный поиск; экспорт; выдача доступа в кабинет
собственника/арендатора.

## 4. Формат находки (строго)

Файл `docs/qa/runs/2026-10-28/<агент>.md`, каждая находка:

```
### <ID агента>-<NN>. <короткий заголовок>
- Приоритет: P0 (теряются/портятся данные, падение) | P1 (сценарий не пройти / ввод сбрасывается / неверные данные) | P2 (неудобно, непонятно, криво) | P3 (косметика)
- Тип: Функционал | Данные | Валидация | UX | Визуал | Документ | Производительность
- Где: URL + элемент
- Шаги: 1… 2… 3…
- Ожидалось: …
- Фактически: … (точный текст ошибки, значения полей до/после)
- Доказательство: SQL-результат / DOM-вывод / строка лога сервера
- Воспроизводимость: 2/2, 1/3 …
```

Не включать в отчёт:
- круглый тёмный значок в углу (индикатор Next.js dev, его нет в проде);
- медленную ПЕРВУЮ загрузку страницы в dev;
- «нет данных» на графике, если данных в базе действительно нет (проверь SQL).

В конце файла — **«Что проверено и работает»** (коротко) и **«Не проверено»** (с причиной).

## 5. Роль командира (оркестратор)

1. Раздать сценарии исполнителям без пересечения по записям (у каждого свой префикс).
2. Получив отчёты — каждую P0/P1 воспроизвести лично; пометить «подтверждено /
   не подтвердилось / не воспроизвёл».
3. Оценить качество работы каждого исполнителя: покрытие (сколько из своих пунктов
   реально пройдено), точность (доля подтвердившихся находок), доказательность.
4. Свести всё в `docs/qa/QA-REPORT-<дата>.md`: таблица P0–P3, источник доказательства,
   что править (файл/компонент), что проверено и работает, что не проверено.
