# UX-аудит «простота использования» — 23.10.2026

Версия на момент аудита: 2.31.1. Проведён 4 параллельными агентами через реальный
UI (тестовый аккаунт `audit-admin@housepro.local`, боевая БД HousePro, без
удаления/правки существующих записей) + чтение кода. Полные транскрипты находок
по модулям в этом файле ниже; детальные переписки агентов не хранятся отдельно.

**Цель аудита**: CRM задумана как простой инструмент для рядового риелтора.
Найти места, где простота потеряна — лишние клики, тупиковые переходы, разорванный
контекст между модулями, дублирующие или нерабочие инструменты.

**Не аудит безопасности/производительности** — те открытые пункты уже есть в
`docs/IMPROVEMENTS.md`. Здесь только usability.

---

## Главный разрыв системы: чек-лист и предусловия не умеют указывать «где это сделать»

Корень большинства находок — один и тот же паттерн по всей системе:
**система знает, что нужно сделать (чек-лист, предусловие, readiness-панель),
но не знает и не показывает, где это физически сделать.** Risk: риелтор видит
требование, но не кнопку.

Подтверждено на трёх независимых участках:

1. **Комиссия на сделке.** Чек-лист стадии `move_in` требует «Получена комиссия»
   (`stage-checklists.ts:66`) — это просто чекбокс прогресса, он не создаёт и не
   связывает ничего в бухгалтерии. Форма транзакции (`TransactionForm`) уже
   поддерживает `defaultDealId` специально под этот кейс (есть коммент в коде),
   но ни одна ссылка с карточки сделки (`/deals/[id]/page.tsx`) этот параметр не
   передаёт. Единственный путь — Бухгалтерия → Новая операция → раскрыть
   «Дополнительно» → искать сделку по номеру СД-#### в `<select>` без поиска
   (лимит 100 последних). **Высокая серьёзность.**
2. **Расчёт с собственником в управлении.** Чтобы «закрыть расчёт», нужно пройти
   3-4 экрана: `/management` → карточка → вкладка «Финансы» ИЛИ отдельная
   страница `/settlement` (дублирует тот же функционал) → при необходимости ещё
   `/report`/`/terms`. Два экрана с одинаковым заголовком «Расчёты с
   собственником» — непонятно какой главный. **Критично.**
3. **Создание сущности из контекста сделки.** «Создать объект» (`target="_blank"`,
   без `?deal_id=`), «Добавить контакт» (без привязки к сделке) — после создания
   риелтор должен вручную вернуться и привязать созданное обратно. Контраст:
   `/tasks/new?deal_id=...` делает это правильно (автоподстановка + авто-разворот
   блока связей) — есть эталон в самом проекте, просто не применён везде.

## Второй системный разрыв: один путь перехода стадии — строгий, второй — нет

`DealStageBar` (степпер на карточке) двигает стадию через `updateDealStatusAction`,
который проверяет `canMoveStage` (чек-листы + предусловия). Форма
`/deals/[id]/edit` меняет тот же `deals.status` через `updateDealAction` —
**без этой проверки**. Любой, кто открыл «Редактировать» вместо степпера, может
перескочить всю воронку одним сохранением, обходя смысл всей системы стадий.
**Критично** — это не мелочь, это дыра в целостности данных, ради которой
строилась вся архитектура `directions.ts`/`transitions.ts`.

## Третий разрыв: форма сделки одна для 4 разных процессов

Карточка/форма сделки показывает одинаковый набор полей независимо от
направления: «Собственник», «Банк», «Одобрение банка», «Кадастровый №»,
«Участок», «Торг» — поля продажи недвижимости — видны и в «Подборе для
арендатора», где их смысла нет вовсе. Нарушает собственное правило проекта
(≤6 полей на виду, человеческий язык, единый скелет без уникальных исключений)
не формой-как-таковой, а тем, что форма не слушает выбранное направление.

### Раздражает — лишние клики, путаница, но не ломает работу

- Канбан сделок рисует все пустые колонки воронки подряд — лишний скролл.
- Переход «Показ → Договор/Сделку» отсутствует — контекст контакта теряется.
- Собственник объекта не подтягивается в форму договора при переходе через `?property_id=` (только через `?deal_id=`/`?contact_id=`).
- Завершение показа возможно без выбора результата — ключевая для воронки информация необязательна.
- Панель «Чего не хватает» на карточке договора противоречит видимым полям («не заполнены даты» при видимой дате).
- `/payments` и `/payments/[id]` — чистые редиректы в `/accounting` без сохранения контекста конкретной операции.
- Дубль категории «Прочие доходы» в справочнике.
- Список лидов «засорён» техническими заявками Авито («сообщение не поддерживается») — искажает счётчик «Новых лидов» на дашборде.
- 14 пунктов в «Настройках» одним плоским списком — для агентства 3-5 человек реально нужны 4-5 (Компания, Тарифы, Авито, Шаблоны, Сотрудники); API/Webhooks/Audit/приём платежей через ЮKassa — для крупных команд.
- «Тарифы агентства» (комиссии с клиентов) и «Приём платежей» (ЮKassa) конфликтуют по названию с ожиданием «подписка на CRM» — отличие объяснено только текстом внутри одной из страниц.
- Два похожих способа продвинуть лид в канбане (drag-n-drop и кнопка «→ Контакт») без объяснения разницы.
- Два пути создать контакт на форме договора («модалка» и «→ открыть форму»).
- Мастер «Оформить сделку» доступен с самой первой стадии, когда данных для договора ещё нет.

### Мелочи — стоит поправить заодно, не приоритет

- Drag-n-drop на канбане сделок разрешает перетащить карточку куда угодно, а потом откатывает с toast об ошибке — лучше заранее показывать недоступные колонки.
- OverflowMenu на завершённой/отменённой сделке всё равно предлагает «Запланировать показ»/«Договор вручную».
- Источники лида («Авито», «ЦИАН») показываются одинаково для всех направлений, хотя для «Подбора» неприменимы.
- Дублирующая ссылка «+Договор» в блоке «Договоры» и «Договор вручную» в OverflowMenu — одно действие, два места.
- `/accounting/transactions/new`: Deal/Property/Contact списки подгружаются с разными магическими лимитами (100/300/200) без индикатора «показаны не все».
- `/accounting/recurring`: «Сгенерировать сейчас» выглядит как второй способ создать операцию.
- ⌘K по клику мышью не подтверждён как рабочий (не проверено до конца из-за нестабильности тест-браузера — требует ручной проверки).

## Предложение: как переосмыслить логику (простой вариант, не усложняя)

Вместо точечных патчей на каждую находку — три структурных решения, которые
закрывают основную массу находок одним и тем же механизмом.

### Решение 1 — Единая точка перехода стадии

Весь код, который меняет `deals.status`, должен идти через один и тот же путь
с проверкой `canMoveStage`. Сейчас их два (степпер — строгий, `edit`-форма —
нет). Правило: **стадия меняется только через степпер или через мастер
«Оформить»; в форме редактирования поле «Стадия» убирается совсем** (риелтору
незачем менять стадию из формы правки прочих полей — это разные действия).
Закрывает K1, K2 одним ходом.

### Решение 2 — Чек-лист пунктов умеет указывать действие

Добавить в `ChecklistItem` необязательное поле:
```ts
action?: { label: string; href: (dealId: string) => string }
```
Непройденный обязательный пункт рисует рядом кнопку-ссылку на точку, где это
закрывается, с автоподстановкой `deal_id` (и `property_id`/`contact_id` где
нужно) через query-параметр — ровно тот паттерн, что уже работает в
`/tasks/new?deal_id=...`. Для «Получена комиссия» — ссылка на
`/accounting/transactions/new?deal_id=...&type=income&category=agency_fee`.
Закрывает K8 и половину находок «раздражает» про разорванный контекст, без
новых экранов и новой логики — переиспользует то, что уже работает в задачах.

### Решение 3 — Карточка/форма сделки показывает поля по направлению

`DealFormBody` уже знает `direction` (используется для чек-листа и степпера).
Поля, специфичные для продажи (банк, кадастровый №, участок, торг), скрываются
в `FormExtra`/не рендерятся вовсе для направлений, где они не нужны —
аналогично тому, как `requiredForContract()` уже выбирает нужные поля договора
по типу контракта (`deal-completion.ts`). Закрывает «форма одна для всех
процессов» без создания четырёх разных форм.

### Решение 4 (точечное, не структурное) — слить дублирующие экраны

- `/management/[id]/settlement` — удалить как отдельную страницу, оставить
  только встроенный блок «Расчёты с собственником» на карточке (один источник
  правды, без дублей).
- `/payments` и `/payments/[id]` — либо удалить из навигации полностью (раз это
  legacy-редирект без контекста), либо сделать настоящим алиасом конкретной
  операции в `/accounting/transactions/[id]`.
- Алгоритм дублей контактов — добавить к совпадению по телефону проверку
  совпадения имени (хотя бы частичного) перед тем, как предлагать слияние.
- Settings: сгруппировать 14 пунктов в 2 видимых уровня — «Основное» (Компания,
  Тарифы, Авито, Шаблоны, Сотрудники, Уведомления) всегда видно; «Для
  разработчиков/продвинутых» (API, Webhooks, Audit, Экспорт фидов) — свёрнуто по
  умолчанию под одним пунктом меню.

## Что НЕ делать (чтобы не наступить на те же грабли)

- Не плодить ещё одну прослойку конфигурации «что требуется на экране» — решение 2
  расширяет существующую структуру `ChecklistItem`, не создаёт параллельный реестр.
- Не делать для каждого направления сделки отдельную форму/страницу — решение 3
  фильтрует поля в существующем компоненте по уже существующему `direction`.
- Не трогать `canMoveStage`/`transitions.ts` — они написаны правильно и с тестами;
  проблема только в том, что не все пути идут через них.
