# HousePro CRM — как мы работаем

Процесс: что сделать до задачи, во время и перед пушем. Правила кода — `AGENTS.md`,
процедуры — skills `housepro-*` (`.hermes/skills/`), приоритеты —
`docs/IMPROVEMENTS.md`, хроника прошлых сессий — `docs/JOURNAL.md`.

Файл короткий намеренно: раньше здесь лежало 27 KB истории сессий, и из-за этого не
читалась ни история, ни сам процесс.

---

## Контекст (сверено 29.10.2026)

- **Контур:** внутренний, живых клиентов нет, единственный пользователь — Руслан.
- **Команда:** Руслан + агент (Hermes). Надолго. Поэтому здесь **нет** CODEOWNERS,
  PR-темплейтов, branch protection, husky/lint-staged — это процесс под команду,
  которой не существует. Не предлагать их снова, пока команда реально не выросла.
- **Приоритет:** открытые пункты `docs/IMPROVEMENTS.md` в порядке таблицы, затем
  фичи. Новый техдолг не чинить на автомате: сформулировать, предложить, дождаться
  приоритезации.
- **Философия тестов:** не покрытие, а регресс-защита. Важно, чтобы новая фича не
  тихо ломала старую.

## Перед началом задачи

- [ ] `AGENTS.md` грузится сам (Hermes читает его из cwd); процедуры — по skills,
      не по памяти.
- [ ] Работаем в текущем чекауте. Клонировать заново не нужно. Чужие
      незакоммиченные правки в `~/projects/work-space/housepro-crm` не трогать;
      параллельные задачи — в отдельном `git worktree`.
- [ ] Задача трогает схему БД → свериться с `LIST_TABLES` через MCP, а не с
      памятью/документацией, которые отстают.
- [ ] Задача похожа на новую фичу или значимое решение → сначала уточнить у
      владельца границы, а не додумывать.

## Во время разработки

- [ ] Новая форма → только через `ServerActionForm`, без `formAction()`-антипаттерна.
- [ ] Новый Server Component → ноль event handlers, ноль `useState`/`useEffect`.
- [ ] Новый Supabase-клиент в API route → `getSupabaseAdmin()` лениво внутри
      хендлера, с `no-store`. Не копировать инстанциацию в 23-й файл.
- [ ] Новый GET route с данными по org → обязательно
      `export const dynamic = 'force-dynamic'`.
- [ ] Новая RLS-политика → без сабквери к той же таблице (через
      `get_user_org_id()`), в `DO $$ BEGIN IF NOT EXISTS ... END $$`.
- [ ] Правишь файл >300 строк → выносишь логику в `features/*/services`.
- [ ] Меняешь денежный/юридический поток (payments, contracts, billing) → тест на
      этот поток обязателен.

## Перед пушем (обязательно, без исключений)

> Полная процедура — skill `housepro-release`. Пуш без зелёной проверки блокирует
> хук `scripts/agent-hooks/guard-bash.mjs`.

- [ ] `npm run check` зелёный (шаги не нумеруются — список в шапке
      `scripts/pre-push-check.mjs`).
- [ ] Версия поднята тем же коммитом, если правился `src/` или миграции.
- [ ] Живой прогон по затронутым экранам + Playwright, если изменение значимое.
- [ ] `README.md` обновлён тем же коммитом, если появился новый модуль.
- [ ] Глава `docs/handbook/` поправлена, если изменилось поведение раздела.
- [ ] `.env.local` с плейсхолдерами удалён, если создавался для проверки.
- [ ] Миграция закоммичена вместе с кодом, не отдельным пушем потом.
- [ ] Push по уже настроенному `origin`. **Токен в URL не использовать** — он
      оседает в `git remote -v`, в истории шелла и в логах; хук такую команду
      блокирует.
- [ ] Сеть (git/gh/npm) — через `env -u HTTPS_PROXY -u HTTP_PROXY`.

## Ветка, PR, слияние

- Работа — в своей ветке (`fix/…`, `chore/…`, `feat/…`), отправка — PR в `main`.
  Прямой пуш в `main` не делаем.
- **Коммит, пуш и слияние — три отдельных разрешения.** Правки можно держать в
  рабочей копии и поднимать версию; `git commit` — после «коммить»; пуш — в свою
  ветку; слияние — после отдельного «сливай», с зелёными чеками.
- Перед PR проверить, что в ветке нет чужих коммитов: `git log --oneline
  origin/main..HEAD` и `git diff --stat origin/main` должны совпадать с задачей.

## После завершения фазы/фичи

- [ ] Обновить `README.md` (таблица «Возможности»), если появился новый модуль.
- [ ] Закрытые пункты отметить в `docs/IMPROVEMENTS.md`, факты о процессе — в
      `docs/JOURNAL.md` (хроника, не правила).
- [ ] Урок, который пригодится снова, — в skill (`housepro-*`), а не в память чата:
      процедуры живут в skills, факты — в документах репозитория.

## Красные флаги — остановиться и спросить, а не додумывать

- Документация утверждает одно, код — другое → **доверять коду**, расхождение
  зафиксировать и сообщить.
- Задача подразумевает необратимое изменение данных (удаление, `DROP`, массовый
  `UPDATE`) → согласие владельца обязательно, бэкап — в репозиторий.
- Задача пахнет процессной бюрократией «для команды» → сверить с этим файлом:
  команда — два человека, бюрократия не нужна, пока не сказано обратное.
- Обещание владельцу вида «после слияния будет на домене» → сначала проверить, куда
  реально смотрит прод (`getent ahosts` + запрос страницы).
