# Итоговый аудит HousePro CRM — для анализа другой моделью
**Дата: 26.10.2026 · Снимок кода: ветка `fix-meters-process-button`, актуальный коммит на момент аудита**

Этот документ сводит два независимых прохода:
1. **Функциональный аудит** (бизнес-логика, безопасность, живое воспроизведение на
   изолированном локальном Supabase-стенде с тестовой организацией «Смоук Тестов»)
2. **UI-аудит** (скриншоты 1280px + разбор vision-моделью + верификация через DOM/код)

Каждая находка несёт метку доказательства:
- **[воспроизведено живьём]** — баг реально вызван через UI/API на тестовом стенде, с логами/БД-доказательством.
- **[DOM-подтверждено]** — факт верстки проверен через `scrollWidth`/`getComputedStyle`/прямой код.
- **[статический анализ]** — найдено чтением кода, не воспроизведено динамически.
- **[НЕ подтвердилось]** — гипотеза проверена и отклонена; оставлено для прозрачности, чтобы следующая модель не тратила время на повтор.

---

## Как получены данные

- Локальный изолированный стенд: Docker + `supabase start` (образы Supabase CLI), 65 миграций применены, тестовая организация и пользователь созданы через Auth Admin API, затем залогинены штатным UI-флоу.
- Production-доступ (housepro24.ru) — только read-only, без мутаций.
- Межорганизационный RLS-тест — создана вторая изолированная организация и пользователь, проверка через прямые PostgREST-запросы с живым JWT второго пользователя (не через сервисную роль).
- Сбои записи в БД симулировались временными PL/pgSQL-триггерами (`BEFORE UPDATE ... RAISE EXCEPTION`), которые удалены сразу после теста — в репозитории и БД не осталось следов.
- Все тестовые данные помечены префиксом `__smoke__` для последующей идентификации и очистки.

### P0-1. Конвертация лида даёт ложный успех при сбое записи — ✅ ИСПРАВЛЕНО (v2.40.4)

### P0-2. Кнопка «Исправить статус» объекта не исправляет показанный ею сценарий — ✅ ИСПРАВЛЕНО (v2.40.4)
**Статус:** исправлено и проверено живьём. Кнопка теперь чинит оба направления
(`available` + подписанный договор → `rented`; `rented` без договора →
`available`), а при неподписанном договоре прямо объясняет, почему статус
менять нельзя. Панель «Чего не хватает» показывает находку тоже только по
подписанному договору — панель и кнопка больше не расходятся.
Правило вынесено в чистую функцию `src/features/properties/lib/property-status-fix.ts`
и покрыто тестами.

### Исходное описание находок (для истории)
**Файл:** `src/features/leads/actions/leads.actions.ts:283-291` (функция `convertLead`)

```ts
await supabase
  .from('leads')
  .update({ status: 'converted', contact_id: contactId, updated_at: ... })
  .eq('id', id)
// ← error не проверяется
redirect(createDeal ? `/deals/new?contact_id=${contactId}` : `/contacts/${contactId}`)
```

**Воспроизведено:** временный триггер на `leads`, блокирующий переход в статус
`converted`, был установлен → клик «Создать сделку» на карточке лида → сервер
вернул 200, браузер перенаправлен на `/deals/new?contact_id=...` как при
полном успехе → проверка БД показала: **лид остался `status='new'`,
`contact_id=NULL`**, при этом **контакт для него уже был создан** (строка
263-280 этой же функции, отдельный insert, который прошёл раньше update).

**Последствия:** пользователь видит экран «Новая сделка» с предзаполненным
контактом и считает конвертацию успешной. Лид навсегда остаётся «Новым» в
статистике и воронке, хотя контакт для него уже существует в базе. При
повторной попытке конвертации по тому же номеру телефона код (строка 252-253)
найдёт существующий контакт и не создаст дубль, но сам лид не исчезнет из
статуса «Новый», искажая конверсионную статистику навсегда, если риелтор не
заметит и не закроет лид вручную.

**Исправление:** проверить `{ error }` после update, не делать redirect при
ошибке, вернуть пользователю `{ error: friendlyDbError(error, ...) }`.
Рассмотреть транзакционность (RPC) для связки insert-contact + update-lead,
т.к. частичный успех (контакт есть, лид не обновлён) — отдельная проблема
данных независимо от обработки ошибки.

### P0-2. Кнопка «Исправить статус» объекта не исправляет показанный ею сценарий
**Файлы:** `src/features/properties/actions/properties.actions.ts:194-247`
(`fixPropertyStatusAction`) vs `src/lib/readiness.ts:129-149` (`checkProperty`)

Панель «Чего не хватает» на карточке объекта показывает критичную находку
**«По объекту есть договор аренды, но статус — «Доступно»»** (срабатывает при
`hasActiveRentContract === true && status === 'available'`, `readiness.ts:132`)
с кнопкой «Исправить» рядом (UI-паттерн из закрытой находки K4 прошлого аудита).

Но сама функция `fixPropertyStatusAction` обрабатывает **только обратный
случай**:
```ts
const targetMismatch = property.status === 'rented' && !hasActiveRentContract
if (!targetMismatch) {
  return { error: hasActiveRentContract
    ? 'По объекту есть действующий договор аренды — статус менять не нужно'
    : 'Статус уже соответствует данным договора' }
}
```

**Воспроизведено:** создан объект со статусом `available` + подписанный
договор аренды (`rent_apartment`, `status=signed`) на этот объект → панель
показала критичную находку с кнопкой «Исправить» → клик вернул 200 (без
видимой ошибки в UI, toast не зафиксирован) → **статус объекта не
изменился**, остался `available`.

**Последствия:** риелтор видит критичную проблему с явной кнопкой «исправить
одним кликом», нажимает — ничего не происходит, без объяснения почему.
Решение K4 из прошлого аудита закрыло только половину проблемы (откат
ошибочного «Сдано» на «Доступно»), но панель продолжает предлагать то же
действие для противоположного и гораздо более частого сценария (забыли
проставить «Сдано» после подписания договора).

**Исправление:** либо расширить `fixPropertyStatusAction`, чтобы он
обрабатывал оба направления рассинхрона (`available→rented` при наличии
активного договора, не только `rented→available` при его отсутствии), либо
не показывать кнопку «Исправить» на панели для направления, которое функция
не умеет чинить — сейчас кнопка обещает действие, которого не выполняет.

## P1 — Высокий приоритет (статический анализ + частичная верификация)

### P1-1. `advanceDealStage` не проверяет ошибку записи при автоматическом продвижении стадии
**Файл:** `src/lib/deal-automation.ts:53`

```ts
await supabase.from('deals').update({ status: target }).eq('id', dealId)
// ← error не проверяется, функция возвращает void
```

Вызывается из 6 разных мест (`contracts.actions.ts:189,325`,
`collections.actions.ts:210`, `engagements.actions.ts:153`,
`complete-deal.actions.ts:386`, `bank-import.actions.ts:253`,
`accounting.actions.ts:514`) — при подписании договора, оплате, завершении
сделки. Ни один вызывающий код не проверяет результат.

**Частично воспроизведено:** в отличие от ручного продвижения через степпер
(`updateDealStatusAction`, которая КОРРЕКТНО обрабатывает ошибку и
останавливает операцию — подтверждено живьём через тот же триггер), для
автоматического пути через `advanceDealStage` тест технически не дошёл до
момента реального UPDATE (целевая и текущая стадия совпали из-за ограничений
подготовки сценария). Код однозначно не проверяет ошибку, но живое
доказательство сбоя именно в этом пути не получено в данной сессии.

**Для следующей сессии:** продвинуть тестовую сделку на одну стадию до
точки, где `stageForMilestone` вернёт стадию СТРОГО дальше текущей
(`targetIndex > currentIndex`), затем заблокировать UPDATE триггером и
подписать договор/завершить сделку — проверить, молчит ли автоматика при
сбое.

### P1-2. Межорганизационный доступ к договорам — НЕ подтвердилось как уязвимость
**[НЕ подтвердилось]** Файл: `src/features/contracts/actions/contracts.actions.ts:221-222,256-284`

Исходная гипотеза (от параллельного субагента): `updateContractAction` и
`deleteContractAction` фильтруют запрос только по `id`, без явного
`organization_id` — потенциальная дыра межорганизационного доступа.

**Проверено живьём:** создана вторая изолированная организация и
пользователь, получен его реальный JWT через `/auth/v1/token?grant_type=password`,
выполнены прямые PostgREST-запросы (не через сервисную роль — через обычную
аутентифицированную сессию) к договору первой организации:
- `SELECT` → пустой массив (RLS скрывает чтение)
- `PATCH status='terminated'` → 0 затронутых строк, запись не изменилась
- `DELETE` → 0 затронутых строк, запись осталась в БД

RLS-политика в `00000000000001_baseline_snapshot_indexes_rls_functions.sql:379-389`
(`organization_id = get_user_org_id()`) реально блокирует доступ на уровне
БД. Отсутствие явного `organization_id` в коде Server Action — отступление
от стиля проекта (`src/features/CLAUDE.md:14-15` требует явной фильтрации),
но не доказанная уязвимость при текущих настройках RLS. **Не поднимать как
security-находку без дополнительного основания**; рассмотреть точечный
рефакторинг для consistency (defense-in-depth), не как срочный security-фикс.

## P2 — Средний приоритет

### P2-1. Повторное завершение показа создаёт дублирующую задачу — ✅ ИСПРАВЛЕНО (v2.40.4)
**Статус:** исправлено и проверено живьём: повторное завершение показа с тем же
результатом больше не создаёт вторую задачу (проверено на изолированном стенде —
после второго завершения в БД по-прежнему одна задача). Перед вставкой задача
ищется по `lead_id` + теме среди незакрытых.
**Файл:** `src/features/showings/actions/showings.actions.ts:100-127`

```ts
if (status === 'completed' && result && updated?.lead_id) {
  if (result === 'interested') {
    ...
    await supabase.from('tasks').insert({ title: 'Связаться повторно по показу', ... })
```

Вставка задачи ничем не защищена от дублирования — ни проверкой
существующей задачи с тем же `lead_id`+темой, ни идемпотентным ключом.

**Воспроизведено живьём:** показ завершён со статусом `completed`+`interested`
→ задача создана (1 шт, подтверждено в БД) → показ откачен обратно в
`planned` напрямую через БД (имитация повторного открытия/ретрая) → показ
завершён второй раз тем же статусом → **вторая идентичная задача создана**
для того же лида (подтверждено в БД: 2 записи `title='Связаться повторно по
показу'`, разные `id`, тот же `lead_id`). Видно на карточке лида как дубль
в UI.

**Исправление:** перед insert проверить, нет ли уже открытой задачи с тем же
`lead_id` и темой/источником (например, по `description` с привязкой к
`showing_id`, если такое поле добавить), либо сделать показ неизменяемым
после `completed` на уровне формы (сейчас это возможно только через прямой
API/откат в БД, что менее вероятно в реальном использовании, но не
невозможно при сетевых ретраях формы).

### P2-2. Невалидные числовые условия договора блокируют отправку формы без сообщения об ошибке
**Файл:** форма `/contracts/new` (client-side), возможно связано с Zod-схемой
в `src/features/contracts/actions/contracts.actions.ts:47-63` (`parseContractTypeData`)

**Воспроизведено:** поле «Количество детей» (`<input type="number" min="0">`)
получило значение `-5` через JS (`value` setter) → клик/JS-клик/
`form.requestSubmit()` на кнопке отправки → **ни один вариант не инициировал
HTTP-запрос** (подтверждено отсутствием новой строки в сервер-логе после
клика) → с валидным значением (2) та же форма отправилась успешно за один
клик.

**Важное уточнение:** это НЕ подтверждает гипотезу «сервер молча заменяет
невалидные условия на `{}}`» (`parseContractTypeData` строки 53-62) — это
другой, более ранний барьер: **браузерная/React клиентская валидация не
даёт запросу уйти на сервер вовсе**, без какого-либо сообщения пользователю
о причине. Кнопка просто не реагирует. Нарушает правило проекта №6
(«Человеческий язык: ошибка говорит, что случилось и что делать») — здесь
нет вообще никакого сообщения.

**Для следующей сессии:** серверная ветка `parseContractTypeData` (молчаливая
замена на `{}}` при провале Zod) всё ещё не проверена живьём — нужен способ
обойти клиентскую валидацию (например, прямой POST к Server Action с нужным
`Next-Action` заголовком, или временное отключение HTML5 `min` атрибута
через DOM перед отправкой) для честной проверки серверного пути.

## Нерешённые вопросы для следующей сессии

1. Довести до конца живой тест P1-1 (`advanceDealStage` при реальном
   следующем-за-текущим milestone).
2. Проверить серверную ветку `parseContractTypeData` (молчаливый `{}}`)
   без участия клиентской валидации.
3. Проверить реестр объектов/сделок/договоров на горизонтальное
   переполнение при РЕАЛЬНОМ количестве строк (текущий тест — 1-2 строки,
   недостаточно для оценки сценария с десятками записей).
4. Степпер стадий сделки — замерить фактическое поведение `flex-wrap` на
   1280/1440/1920px через `getBoundingClientRect`, не только по скриншоту.
5. Очистка тестовых данных `__smoke__` в изолированной БД перед сдачей
   стенда — локальный Docker-стенд можно просто остановить
   (`supabase stop`) и/или удалить контейнеры, т.к. это не production.
