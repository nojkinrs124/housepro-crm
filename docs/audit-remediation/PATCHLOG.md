## Что исправлено в данных (прод, `accounting_transactions`)

1. Удалено 35 операций `type=income, status=completed` без `paid_at`,
   созданных одним батчем `created_at=2026-09-22`, с `date` вплоть до

2. Удалены все 38 `status=planned` операций — автогенерированный график

3. Удалены 37 операций `type=expense, category=owner_payout` — симметричная
   расходная сторона той же задним-числом истории (создана тем же батчем

   `docs/audit-remediation/deleted-accounting-transactions-backup-expenses.json`.

Все удаления затронули ТОЛЬКО операции, привязанные к `engagement_id` из
батча 22.09 — 31 ручная операция без `engagement_id` (день-в-день, реальные
комиссии/платежи сотрудников) не тронута, несмотря на тот же пустой `paid_at`.

## Почему `paid_at` не был надёжным маркером сам по себе

`paid_at` заполняется ТОЛЬКО когда операцию проводят через
`completeTransactionAction` (инлайн-кнопка «Отметить оплаченным») или через
`updateTransactionAction` при смене статуса на `completed`. Ручная форма
создания операции (`createTransactionAction`) никогда не писала `paid_at`,
даже если пользователь сразу указывал статус «Выполнено» — поэтому 31 живая
ручная операция визуально была неотличима от фиктивного бэкфилла по одному
только признаку «есть/нет `paid_at`». Отличие нашли по вторичным признакам:
привязка к `engagement_id`, пачковый `created_at`, дата из прошлого.

### Фикс бага (код)

`src/features/accounting/actions/accounting.actions.ts` →
`createTransactionAction`: при `status === 'completed'` теперь сразу
проставляется `paid_at = new Date().toISOString()`, как и в
`completeTransactionAction`/`updateTransactionAction`. Следующий такой же
бэкфилл будет виден по пустому `paid_at`, не требуя вторичных признаков.

## HL-01 — Конвертация лида: ошибка записи больше не выдаётся за успех (P0-1)

**Причина.** `convertLead()` обновлял лид (`status='converted'`, `contact_id`)
и сразу делал `redirect()` на `/deals/new`, не проверяя `{ error }`. При сбое
(RLS, ограничение, сеть) пользователь попадал на экран новой сделки как при
успехе, а лид оставался «Новым»; при этом контакт, созданный этим же вызовом,
оставался в базе без связи с лидом — «сирота», который потом невидим в работе.

**Изменение.** `src/features/leads/actions/leads.actions.ts`:
- результат обновления проверяется (`error` **и** ноль обновлённых строк —
  оба случая считаются провалом);
- при провале возвращается ошибка вместо редиректа (пользователь остаётся на
  карточке лида и видит текст);
- контакт, созданный **этим** вызовом, удаляется; найденный по телефону
  существующий контакт не трогается (он принадлежит другой истории).

**Проверка.** Триггер `BEFORE UPDATE` на `leads`, блокирующий переход в
`converted` → клик «Создать сделку»: остались на `/leads/{id}`, появился баннер
«Не получилось сохранить лид…», в БД `status='new'`, `contact_id=null`,
контактов с этим телефоном — 0 (сироты нет). После снятия триггера конвертация
проходит как раньше.

**Риск.** Если удаление «своего» контакта не удастся (RLS), останется сирота —
поведение в этом случае не хуже прежнего; ошибка пользователю всё равно показана.

## HL-02 — «Исправить статус» объекта чинит оба направления (P0-2)

**Причина.** `checkProperty()` показывал блокер и для «подписанный договор +
статус Доступно», и для «Сдано без договора», а `fixPropertyStatusAction()`
умел только второе (`rented → available`). Кнопка «Исправить» рядом с первой
находкой вызывалась, возвращала 200 и **ничего не меняла**.

**Изменение.**
- Новый чистый модуль `src/features/properties/lib/property-status-fix.ts`:
  `decidePropertyStatusFix()` возвращает `update` (nextStatus) либо `noop` с
  человеческим текстом причины.
- `fixPropertyStatusAction()` использует это правило, пишет аудит-лог с
  фактическим новым статусом.
- «Сдан» ставится только по **подписанному** договору (`signed`/`completed`) —
  черновик не делает объект занятым (сохранено прежнее решение владельца по K4);
  в этом случае кнопка прямо говорит «договор ещё не подписан».
- `src/lib/readiness.ts`: находка `property.rented_but_available` показывается
  тоже только по подписанному договору (`hasSignedRentContract`, с обратной
  совместимостью для старых вызовов). Панель и кнопка больше не расходятся.
- `src/app/(dashboard)/properties/[id]/page.tsx` передаёт новый флаг.

**Проверка.** Объект `available` + подписанный `rent_apartment` → панель
показала блокер с новым текстом → клик «Исправить» → статус в БД `rented`,
блокер исчез, осталось только предупреждение о координатах.

**Риск.** Проданные/неактивные/зарезервированные объекты намеренно не
переводятся: договор аренды о них ничего не говорит.

## MD-01 — Показ не создаёт вторую задачу-напоминание (P2-1)

**Причина.** Задача «Связаться повторно по показу» вставлялась безусловно при
каждом завершении показа с результатом «заинтересован». Повторное завершение
(возврат статуса, ретрай, повторное открытие) давало дубль на карточке лида.

**Изменение.** `src/features/showings/actions/showings.actions.ts`: тема задачи
вынесена в константу, перед вставкой ищется незакрытая задача с тем же
`lead_id` и той же темой; найденная — вторая не создаётся.

**Проверка.** Показ завершён → 1 задача; показ возвращён в `planned` и завершён
повторно тем же результатом → по-прежнему **1** задача (до правки было 2).

**Риск.** Если риелтор осознанно закрыл задачу и хочет новую после повторного
показа — она создастся, потому что закрытые (`done`) в проверку не попадают.

## MD-02 — Сбой автоматического продвижения сделки виден в логе (P1-1)

**Причина.** `advanceDealStage()` делала `update({status})` без проверки
`error`: при сбое сделка оставалась на прежней стадии, а вызывающий код

## B-02 — Невалидное число в «Условиях договора» блокирует submit без сообщения

**Причина.** Поля вроде «Количество детей» (`type="number" min={0}`) лежат
внутри свёрнутого по умолчанию `<FormExtra>` (`<details>`). Браузер не
генерирует событие `submit`, если форма невалидна, — значит, ни один
JS-обработчик `onSubmit`/`action` не срабатывает. Если невалидное поле к
тому же спрятано в закрытом `<details>`, браузер и не показывает свою
стандартную подсказку: при клике «Создать договор» не происходит вообще
ничего — ни ошибки, ни навигации, ни новой строки в сетевом логе. Пользователь
не может понять, почему кнопка «не работает».

**Изменение.** `src/features/contracts/components/ContractForm.tsx`:
кнопка submit получила `onClick`-перехватчик, который (до того, как браузер
молча откажет в отправке) проверяет `form.checkValidity()`; если форма
невалидна — находит первое `:invalid`-поле, раскрывает его `<details>`
(если был закрыт), скроллит к полю и вызывает `form.reportValidity()`, чтобы
браузер показал свою стандартную подсказку прямо на поле.

**Проверка.** На локальном стенде: «Количество детей» = `-5`, секция
«Условия договора» свёрнута → клик «Создать договор» → секция автоматически
раскрылась, фокус встал на поле, видна подсказка «Значение должно быть больше
или равно 0.» (подтверждено скриншотом). Исправление значения на `1` и повтор
клика → форма отправилась, договор создан (`POST /contracts/new 200`,
`createContractAction` в логе), тестовая запись удалена после проверки.

**Риск.** Перехват общий для всех типов договора (срабатывает на любое
`:invalid` поле формы, не только `children_count`) — не специфичен для одного
поля, так что покрывает и другие числовые ограничения в «Условиях договора»
без отдельных правок на каждое поле.

## B-03 — Невалидные условия договора молча заменялись на `{}` на сервере

**Причина.** `parseContractTypeData()` при провале Zod-схемы (битый JSON,
или ЛЮБОЕ поле не прошло проверку — одна пустая строка в описи имущества или
нечисловое значение после прямого POST в обход клиентской валидации)
возвращала просто `{}`. Договор при этом создавался/обновлялся как обычно,
без единой ошибки где-либо — вся заполненная юридическая информация (дети,
животные, неустойка, опись имущества, акт приёма-передачи) терялась без
следа. Воспроизведено напрямую POST-ом в `createContractAction`, минуя
клиентскую валидацию: передан валидный на вид payload с одним невалидным
полем (`cohabitants[0].full_name = ''`, схема требует `min(1)`) — договор
сохранился успешно, но `contract_type_data` в БД оказался `{}` — все 6
остальных валидных полей (`children_count: 2`, `pets_allowed: true` и т.д.)
тоже пропали, а не только проблемное.

**Изменение.** `src/features/contracts/actions/contracts.actions.ts`:
`parseContractTypeData()` теперь возвращает `{ success: true, data }` либо
`{ success: false, error }` с текстом конкретной причины (путь поля +
сообщение Zod). `createContractAction` и `updateContractAction` при провале
сразу возвращают ошибку пользователю и НЕ сохраняют договор — в `updateContractAction`
проверка перенесена перед вставкой строки версии (`contract_versions`), чтобы
при провале не оставался бесполезный снимок версии без реального изменения.

**Проверка.** Прямой POST в обход клиентской валидации с невалидным
`cohabitants[0].full_name`: раньше — договор создавался, `contract_type_data`
= `{}`, данные потеряны без следа; теперь — форма показывает «Условия
договора: «cohabitants.0.full_name» — Too small: expected string to have
>=1 characters», в БД контрактов не прибавилось (было 2, осталось 2).
Повторный тест с валидным payload (тот же набор данных, но `full_name`
заполнено) — договор создан, `contract_type_data` содержит все 7 полей
без потерь. `npx tsc --noEmit` чисто.

**Риск.** Сообщение показывает технический путь поля и текст Zod на
английском (`Too small: expected string...`) — не переведено на понятный
риелтору язык для каждого конкретного поля; для первой версии фикса это
приемлемо (явная ошибка лучше тихой потери данных), но стоит заменить на
точечные `message:` в схемах, если такие отказы станут частыми в проде.

## B-06 — Поиск дублей контактов: нечёткое совпадение имён

**Согласование.** Через `clarify` владелец выбрал критерий схожести: «одно
имя — подмножество слов другого», минимум 2 общих токена (а не приглушённый
текст без логики и не отдельный свёрнутый блок «Ещё»).

**Причина.** `findDuplicateContactsAction`/`mergeContactsAction` требовали
побуквенного совпадения нормализованного `full_name` — пара с общим
телефоном, но разным написанием имени («Иван Иванов» / «Иван Петрович
Иванов», с отчеством и без) не считалась дублем вовсе, хотя для риелтора это
очевидно один человек. Прежняя логика была осознанно консервативна («не
предложить дубль лучше, чем слить чужих людей» — находка K6 прошлого аудита),
но пропускала слишком много реальных случаев.

**Изменение.** `src/features/contacts/actions/duplicates.actions.ts`: новая
чистая функция `namesAreSimilar(a, b)` — true при точном совпадении ИЛИ
если множество слов короткого имени целиком входит в множество слов длинного
(минимум 2 общих токена — одно совпавшее слово типа «Иван» само по себе не
считается, иначе любые два тёзки с общим телефоном стали бы кандидатом).
`findDuplicateContactsAction` строит группу по этому правилу вместо строгого
равенства; серверная защита в `mergeContactsAction` (блокирует слияние при
общем телефоне и разных именах) сверена с тем же предикатом — иначе панель
предложила бы пару, которую сервер тут же отклонил бы при попытке слить, и
кнопка выглядела бы сломанной. `src/app/(dashboard)/contacts/duplicates/page.tsx`:
убрана собственная копия старого строгого фильтра — она применяла свою
проверку ПОВЕРХ уже отфильтрованного списка из `findDuplicateContactsAction`
и отбрасывала именно те пары, которые новое правило должно было разрешить
(правка на сервере не доходила до экрана).

**Проверка.** На стенде: контакт `210e4e0e-...` переименован в «Иван
Петрович Иванов» с тем же телефоном, что у «Иван Иванов» (`fceb92fe-...`) —
`/contacts/duplicates` показал группу «1 группа, 2 карточки» (раньше бы не
показал вовсе). Контакт переименован в «Пётр Сидоров» с тем же телефоном —
страница вернулась к «Дублей не найдено» (разные люди не предлагаются,
безопасная сторона сохранена). Имя восстановлено к исходному «Иван Иванов».
`npx tsc --noEmit` чисто.

**Риск.** Пары с ровно одним общим словом («Иван» + «Иван Петров») по-прежнему
не считаются похожими (порог — минимум 2 токена) — это осознанный компромисс
в пользу меньшего числа ложных совпадений, а не недосмотр.

# BOT-01..07 — Аудит Telegram-бота @HouseProAI_bot — 28.10.2026

Разбор по исходникам (`src/lib/telegram/**`), не по карте. Найдено 7 дефектов
в трёх местах, где расходятся слои доступа и смысла. Работа шла в рабочей
копии, без изменений прод-данных; версия не поднималась.

## BOT-01 — Сотрудник обходил ролевые ограничения через LLM-диалог (P0)

**Причина.** Экраны меню и кнопки уже ролевые (`MEMBER_SCREENS`), а инструменты
ассистента роль не проверяли вовсе: `dispatchReadOnlyTool`/`executeConfirmedMutation`
не принимали актёра. Сотрудник, которому экран «Деньги» закрыт намеренно,
спрашивал текстом «сколько заработали» и получал ответ.

**Изменение.** `features/telegram/services/access.ts` — `ADMIN_ONLY_TOOLS`
(деньги + канал) и `canUseTool(role, tool)`; `tools.ts` — `toolDefinitionsFor(role)`
(модель не видит закрытых схем), проверка роли в диспетчере и в исполнении
подтверждённой мутации (батч живёт в БД между апдейтами — допуск мог измениться);
`turn.ts` отдаёт модели набор по роли; `executeConfirmedMutation(action, payload, actor)`.

**Проверка.** `telegram-tool-permissions.test.ts` (роли, расхождение списков со
схемой, контракт параметров).

**Риск.** Сотрудник больше не получит ответ по деньгам/каналу от ассистента —
это и было целью; кнопки, где доступ уже считался (ownerpay), не менялись.

## BOT-02 — `get_deals(deal_type)` молча игнорировался (P1)

**Причина.** Параметр объявлен в схеме, диспетчер его не передавал, а
`GET /api/v1/deals` его не читал. Модель уверенно пересказывала
неотфильтрованное как отфильтрованное.

**Изменение.** `tools.ts` передаёт `deal_type`; роут `deals` фильтрует по нему.

**Проверка.** Тест «каждый объявленный параметр читается как `args.<name>`» —
падает на исходной версии этого бага.

## BOT-03 — Денежные сводки считались по одной странице (P1)

**Причина.** `get_finance_summary`/`get_finance_chart` брали `limit=200` и
суммировали вернувшуюся страницу; при 200+ операциях в периоде ответ «сколько
заработали» молча занижался.

**Изменение.** Новый канонический расчёт `features/accounting/services/finance-summary.ts`
(чистая функция) + эндпоинт `GET /api/v1/accounting/summary` (постраничный обход
всей выборки). Бот и график считают по нему. `meta.summary` в
`/accounting/transactions` остался прежним, но помечен `summary_scope: 'page'`,
чтобы его снова не приняли за итоги периода.

**Проверка.** `finance-summary.test.ts` (300 строк → сумма всех, а не первых 200).

## BOT-04 — «Доход» в боте считался иначе, чем в CRM (P1)

**Причина.** Бот суммировал `type='income'` плоско; витрина с 27.10.2026 делит
поток на реальную выручку агентства и транзит клиентов (`money-classification.ts`).

**Изменение.** `summarizeFinance` считает тем же предикатом `isAgencyRevenue` /
`isAgencyExpense`: `agencyRevenue` (доход), `transitIncome` (аренда жильцов,
депозиты), `ownerPayouts`, `receivable`, `byMonth`. В ответ инструмента добавлена
подсказка модели, что называть доходом; график подписан «Доход и расход агентства».

**Проверка.** Тесты транзита/выплат/расходов «за счёт собственника».

## BOT-05 — Текст и голос шли по разным цепочкам (P1)

**Причина.** Цепочка «состояния, которые ждут ввод» была собрана дважды:
для текста в `message.ts` и урезанной копией для расшифровки голоса. Голосом
нельзя было ответить на форму добавления пользователя и на расписание/рубрики,
а приоритет открытой сессии «Занести в CRM» был противоположным (в голосе —
первым, в тексте — после CRM-поиска).

**Изменение.** `handlers/pending-input.ts` — одна функция `routePendingInput`
с фиксированным порядком (формы кнопок → сессия «Занести в CRM»); вызывается и
для текста, и для голоса. Правило «новый перехватчик — в этот файл» записано в шапке.

**Проверка.** `npm run check` (build + тесты), ручной разбор веток message.ts.

**Риск.** Изменения в порядке для голоса — по замыслу; поведение текста сохранено.

## BOT-06 и BOT-07 — Журнал бота и молчащие нажатия (P2)

- Провалившаяся мутация помечалась `confirmed` в `bot_pending_actions` —

  `X-Bot-Requester`, роуты `deals`/`transactions` пишут его в `entityLabel`

- Быстрые кнопки CRM молчали при успехе — добавлен `CRM_ACTION_DONE`.
- Неизвестное действие кнопки (`callback/index.ts`) молчало — теперь отвечает
  «кнопка устарела».
- Мёртвая ветка `generate_contract` в `callback/batch.ts` удалена (ни схема,
  ни исполнитель такого действия не объявляют).

## Что осознанно не делалось
