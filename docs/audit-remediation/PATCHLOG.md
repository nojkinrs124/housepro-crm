# PATCHLOG — исправления по аудиту 26.10.2026

Версия: **2.40.4**. Ветка: `fix-meters-button`. Всё проверено на изолированном
локальном стенде (Docker + `npx supabase start`, организация «Смоук Тестов»);
production-данные не изменялись.

## HL-01 — Конвертация лида: ошибка записи больше не выдаётся за успех (P0-1)

**Причина.** `convertLead()` обновлял лид (`status='converted'`, `contact_id`)
и сразу делал `redirect()` на `/deals/new`, не проверяя `{ error }`. При сбое
(RLS, ограничение, сеть) пользователь попадал на экран новой сделки как при
успехе, а лид оставался «Новым»; при этом контакт, созданный этим же вызовом,
оставался в базе без связи с лидом — «сирота», который потом невидим в работе.

**Изменение.** `src/features/leads/actions/leads.actions.ts`:
- результат обновления проверяется (`error` **и** ноль обновлённых строк —
  оба случая считаются провалом);
- при провале возвращается ошибка вместо редиректа (пользователь остаётся на
  карточке лида и видит текст);
- контакт, созданный **этим** вызовом, удаляется; найденный по телефону
  существующий контакт не трогается (он принадлежит другой истории).

**Проверка.** Триггер `BEFORE UPDATE` на `leads`, блокирующий переход в
`converted` → клик «Создать сделку»: остались на `/leads/{id}`, появился баннер
«Не получилось сохранить лид…», в БД `status='new'`, `contact_id=null`,
контактов с этим телефоном — 0 (сироты нет). После снятия триггера конвертация
проходит как раньше.

**Риск.** Если удаление «своего» контакта не удастся (RLS), останется сирота —
поведение в этом случае не хуже прежнего; ошибка пользователю всё равно показана.

## HL-02 — «Исправить статус» объекта чинит оба направления (P0-2)

**Причина.** `checkProperty()` показывал блокер и для «подписанный договор +
статус Доступно», и для «Сдано без договора», а `fixPropertyStatusAction()`
умел только второе (`rented → available`). Кнопка «Исправить» рядом с первой
находкой вызывалась, возвращала 200 и **ничего не меняла**.

**Изменение.**
- Новый чистый модуль `src/features/properties/lib/property-status-fix.ts`:
  `decidePropertyStatusFix()` возвращает `update` (nextStatus) либо `noop` с
  человеческим текстом причины.
- `fixPropertyStatusAction()` использует это правило, пишет аудит-лог с
  фактическим новым статусом.
- «Сдан» ставится только по **подписанному** договору (`signed`/`completed`) —
  черновик не делает объект занятым (сохранено прежнее решение владельца по K4);
  в этом случае кнопка прямо говорит «договор ещё не подписан».
- `src/lib/readiness.ts`: находка `property.rented_but_available` показывается
  тоже только по подписанному договору (`hasSignedRentContract`, с обратной
  совместимостью для старых вызовов). Панель и кнопка больше не расходятся.
- `src/app/(dashboard)/properties/[id]/page.tsx` передаёт новый флаг.

**Проверка.** Объект `available` + подписанный `rent_apartment` → панель
показала блокер с новым текстом → клик «Исправить» → статус в БД `rented`,
блокер исчез, осталось только предупреждение о координатах.

**Риск.** Проданные/неактивные/зарезервированные объекты намеренно не
переводятся: договор аренды о них ничего не говорит.

## MD-01 — Показ не создаёт вторую задачу-напоминание (P2-1)

**Причина.** Задача «Связаться повторно по показу» вставлялась безусловно при
каждом завершении показа с результатом «заинтересован». Повторное завершение
(возврат статуса, ретрай, повторное открытие) давало дубль на карточке лида.

**Изменение.** `src/features/showings/actions/showings.actions.ts`: тема задачи
вынесена в константу, перед вставкой ищется незакрытая задача с тем же
`lead_id` и той же темой; найденная — вторая не создаётся.

**Проверка.** Показ завершён → 1 задача; показ возвращён в `planned` и завершён
повторно тем же результатом → по-прежнему **1** задача (до правки было 2).

**Риск.** Если риелтор осознанно закрыл задачу и хочет новую после повторного
показа — она создастся, потому что закрытые (`done`) в проверку не попадают.

## MD-02 — Сбой автоматического продвижения сделки виден в логе (P1-1)

**Причина.** `advanceDealStage()` делала `update({status})` без проверки
`error`: при сбое сделка оставалась на прежней стадии, а вызывающий код
(подписание договора, оплата, завершение) считал, что всё прошло.

**Изменение.** `src/lib/deal-automation.ts`: ошибка записи логируется с
`dealId`, текущей и целевой стадией (`[deal-automation] …`). Поведение
осталось «мягким» — исключение не бросается, чтобы не ломать основной сценарий.

**Проверка.** Юнит-тесты `deal-automation` зелёные; живой сбой записи
воспроизведён отдельно под B-01 (см. ниже) — лог появляется, стадия не меняется.

## B-01 — MD-02 доведён: живой сбой записи воспроизведён

**Проверка.** Локальный Docker-стенд: сделка `rent_agent` переведена на
`tenant_check` (строго перед целевой `move_in` для вехи `payment`), затем
временный триггер `BEFORE UPDATE` на `deals` заблокировал запись именно для
этой строки. Вызов `advanceDealStage(supabase, dealId, 'payment')` напрямую
через `tsx` (service-role клиент, без прохода через UI) дал:
`[deal-automation] не удалось продвинуть сделку ... tenant_check → move_in
P0001 smoke_test: blocked deal status update`; статус в БД после вызова —
`tenant_check` (не продвинулся). Триггер и функция удалены, `pg_trigger`
подтверждает 0 строк `smoke%`.

**Код не менялся** — находка подтверждала уже внесённый в MD-02 фикс.

## B-02 — Невалидное число в «Условиях договора» блокирует submit без сообщения

**Причина.** Поля вроде «Количество детей» (`type="number" min={0}`) лежат
внутри свёрнутого по умолчанию `<FormExtra>` (`<details>`). Браузер не
генерирует событие `submit`, если форма невалидна, — значит, ни один
JS-обработчик `onSubmit`/`action` не срабатывает. Если невалидное поле к
тому же спрятано в закрытом `<details>`, браузер и не показывает свою
стандартную подсказку: при клике «Создать договор» не происходит вообще
ничего — ни ошибки, ни навигации, ни новой строки в сетевом логе. Пользователь
не может понять, почему кнопка «не работает».

**Изменение.** `src/features/contracts/components/ContractForm.tsx`:
кнопка submit получила `onClick`-перехватчик, который (до того, как браузер
молча откажет в отправке) проверяет `form.checkValidity()`; если форма
невалидна — находит первое `:invalid`-поле, раскрывает его `<details>`
(если был закрыт), скроллит к полю и вызывает `form.reportValidity()`, чтобы
браузер показал свою стандартную подсказку прямо на поле.

**Проверка.** На локальном стенде: «Количество детей» = `-5`, секция
«Условия договора» свёрнута → клик «Создать договор» → секция автоматически
раскрылась, фокус встал на поле, видна подсказка «Значение должно быть больше
или равно 0.» (подтверждено скриншотом). Исправление значения на `1` и повтор
клика → форма отправилась, договор создан (`POST /contracts/new 200`,
`createContractAction` в логе), тестовая запись удалена после проверки.

**Риск.** Перехват общий для всех типов договора (срабатывает на любое
`:invalid` поле формы, не только `children_count`) — не специфичен для одного
поля, так что покрывает и другие числовые ограничения в «Условиях договора»
без отдельных правок на каждое поле.

## B-03 — Невалидные условия договора молча заменялись на `{}` на сервере

**Причина.** `parseContractTypeData()` при провале Zod-схемы (битый JSON,
или ЛЮБОЕ поле не прошло проверку — одна пустая строка в описи имущества или
нечисловое значение после прямого POST в обход клиентской валидации)
возвращала просто `{}`. Договор при этом создавался/обновлялся как обычно,
без единой ошибки где-либо — вся заполненная юридическая информация (дети,
животные, неустойка, опись имущества, акт приёма-передачи) терялась без
следа. Воспроизведено напрямую POST-ом в `createContractAction`, минуя
клиентскую валидацию: передан валидный на вид payload с одним невалидным
полем (`cohabitants[0].full_name = ''`, схема требует `min(1)`) — договор
сохранился успешно, но `contract_type_data` в БД оказался `{}` — все 6
остальных валидных полей (`children_count: 2`, `pets_allowed: true` и т.д.)
тоже пропали, а не только проблемное.

**Изменение.** `src/features/contracts/actions/contracts.actions.ts`:
`parseContractTypeData()` теперь возвращает `{ success: true, data }` либо
`{ success: false, error }` с текстом конкретной причины (путь поля +
сообщение Zod). `createContractAction` и `updateContractAction` при провале
сразу возвращают ошибку пользователю и НЕ сохраняют договор — в `updateContractAction`
проверка перенесена перед вставкой строки версии (`contract_versions`), чтобы
при провале не оставался бесполезный снимок версии без реального изменения.

**Проверка.** Прямой POST в обход клиентской валидации с невалидным
`cohabitants[0].full_name`: раньше — договор создавался, `contract_type_data`
= `{}`, данные потеряны без следа; теперь — форма показывает «Условия
договора: «cohabitants.0.full_name» — Too small: expected string to have
>=1 characters», в БД контрактов не прибавилось (было 2, осталось 2).
Повторный тест с валидным payload (тот же набор данных, но `full_name`
заполнено) — договор создан, `contract_type_data` содержит все 7 полей
без потерь. `npx tsc --noEmit` чисто.

**Риск.** Сообщение показывает технический путь поля и текст Zod на
английском (`Too small: expected string...`) — не переведено на понятный
риелтору язык для каждого конкретного поля; для первой версии фикса это
приемлемо (явная ошибка лучше тихой потери данных), но стоит заменить на
точечные `message:` в схемах, если такие отказы станут частыми в проде.

## LO-01 — Колонка «Документ» в реестре договоров получила заголовок

**Причина.** Колонка с ссылкой `DOCX` была без `title`: читалась как формат
файла, а не как переход к документу.

**Изменение.** `src/features/contracts/components/ContractsView.tsx`: заголовок
`Документ`, `hideBelow: 'lg'` (как у остальных второстепенных колонок),
`aria-label` со номером договора.

**Проверка.** Реестр договоров — заголовок на месте, на узких ширинах колонка
скрывается.
