## Ловушки

- **Локальный resolver врёт.** `dig housepro24.ru` на сервере отдавал старый IP
  парковки Reg.ru (`95.163.244.138`) из кэша systemd-resolved, и `curl` показывал
  страницу «Домен зарегистрирован в reg.ru» — легко принять за «домен не
  подключён». Истину спрашивай у авторитетных NS и публичного DNS:
  `dig +short @ns1.reg.ru housepro24.ru A`,
  `curl "https://dns.google/resolve?name=housepro24.ru&type=A"`.
  Проверка самого сайта в обход кэша:
  `curl --resolve housepro24.ru:443:76.76.21.21 https://housepro24.ru/robots.txt`.
- **Правка env в Vercel не применяется сама.** После `PATCH .../env/<id>` нужен
  редеплой прода: `POST /v13/deployments` с `{name, project, target:"production",
  deploymentId:<последний production dpl>}`. Сборка ~3–5 минут; статус —
  `GET /v13/deployments/<id>` → `readyState: READY`.
- **Чтение значения env.** В списке `/v9/projects/<id>/env` значения зашифрованы
  (`eyJ2Ij...`). Открытое — только поштучно: `GET /v1/projects/<id>/env/<envId>`.
- `metadataBase` обязателен: без него Next отдаёт относительные canonical/og:url,
  и поисковик считает каноническим тот хост, по которому пришёл.
- **`npm run check` трогает исходники.** Прогон может добавить в рабочую копию
  правки, которых ты не делал (видели `PropertiesView.tsx`). Перед коммитом
  смотри `git status --short`; чужие файлы выноси только `git restore --staged`
  — с `--worktree` правка стирается; восстановить можно только через
  `git cat-file -p <blob> > <file>`, если хеш blob был сохранён до отката.
- **«Флапающий» тест на 5-секундном таймауте часто не флап.** Два теста
  (`accounting.test.ts > отмечает транзакцию оплаченной`,
  `deals.test.ts > редиректит при успехе`) падали в CI и проходили локально —
  выглядело как флап раннера. Причина была конкретной: `completeTransactionAction`/
  `createDealAction` на успешном пути вызывают `dispatchWebhook`, который создаёт
  service-role клиент Supabase и реально ходит в сеть; в CI `NEXT_PUBLIC_SUPABASE_URL`
  — placeholder-домен, запрос висит до таймаута vitest. Прежде чем звать что-то
  «флапом раннера», найди Server Action за тестом и проверь, не делает ли он
  реальный `fetch`/сетевой вызов на успешном пути — если да, замокай его
  (`vi.mock('@/lib/webhooks', () => ({ dispatchWebhook: vi.fn() }))`) рядом с
  остальными моками модуля, а не объясняй провал окружением.
- **Любой новый публичный статический файл или папка (verification-файлы,
  `.well-known/…`, но ТАКЖЕ фото/картинки публичного сайта в `public/`) в
  Next-проекте с глобальным auth middleware нужно явно пустить.** Такой
  middleware обычно редиректит всё неизвестное на `/login` до того, как Next
  успеет отдать файл из `public/`. Добавь точный путь или папку (например
  `/site/`) в список публичных исключений (`PUBLIC_EXACT`/аналог) — иначе
  файл подтверждения Google/Яндекса/любого третьего сервиса, ИЛИ фото на
  странице сайта, будет 307 на `/login` вместо 200.
  Симптом «картинка не грузится только на мобильном» часто вводит в
  заблуждение — кажется, что дело в CSS/responsive/`<Image>` sizes, хотя на
  самом деле десктоп просто обходит проблему через Next Image Optimization
  API (`/_next/image?url=...`, обычно в исключениях middleware отдельно),
  а часть мобильных браузеров/режимов экономии трафика запрашивает оригинал
  файла напрямую и ловит редирект. Диагностика быстрее любого осмотра кода:
  `curl -I <домен>/<путь-к-файлу-из-public>` — 307/302 на `/login` вместо
  200 подтверждает причину за один запрос, без эмуляции мобильного UA
  (подмена UA здесь ничего не меняет — дело в пути, не в браузере).
- **PR, который перестал мержиться, потому что в `main` зашёл другой PR
  раньше** (`mergeStateStatus: DIRTY`, `gh pr merge` отвечает «cannot be
  cleanly created») — не чини конфликт вручную в ветке и не форсь merge.
  Возьми чистый diff только своих файлов относительно общего предка
  (`git diff <merge-base>..<своя-ветка> -- <файлы>`), сохрани патчем,
  переключись на свежий `origin/main`, примени `git apply --3way` и закоммить
  отдельно. Это переносит ровно свою логику без версии/lockfile соседнего PR,
  которые стали базовой причиной конфликта. Закрой старый PR с комментарием,
  что изменения ушли в `main` отдельным коммитом (не сливай и не удаляй его
  молча).
- **Проверка реальной индексации в выдаче.** `site:domain`-запросы к Google и
  Яндексу через браузер почти всегда ловят капчу (и через обычный поиск, и
  через API web_search) — это не признак того, что сайта нет в индексе, это
  защита от автоматических запросов. Bing и DuckDuckGo отвечают на `site:`
  честно без логина и капчи — используй их как первый сигнал. Надёжный статус
  — Search Console / Яндекс.Вебмастер, доступные через их официальные API
  (ниже), не через site:-запросы и не через ручной UI-клик.

## Полный доступ к Search Console и Яндекс.Вебмастеру через API (без пароля)

Если у владельца уже есть Google OAuth client_secret (installed app, см.
`self-hosted-secrets-storage` → OAuth-технику), агент может сделать ВСЁ сам
без единого пароля — владелец только кликает «Разрешить» в своей собственной
залогиненной вкладке.

**Google (Search Console API + Site Verification API + Indexing API):**
1. Один OAuth-поток, запросить сразу все scope разом (повторные согласия на
   каждый отдельный scope раздражают владельца и не нужны):
   `webmasters`, `cloud-platform` (чтобы включить API самому, см. технику
   выше), `siteverification`, `indexing`.
2. Включить нужные API: `searchconsole.googleapis.com`,
   `siteverification.googleapis.com`, `indexing.googleapis.com`
   (через `serviceusage.googleapis.com:enable`, см. выше) — подождать ~15–20 с
   после каждого `enable` перед первым вызовом, иначе 403
   `accessNotConfigured`.
3. **Для домена без `sc-domain:` префикса** (ресурс типа URL-prefix, не Domain
   property) подтверждение владения идёт через Site Verification API —
   `webResource().getToken(body={"site":{"type":"SITE","identifier":url},
   "verificationMethod":"META"})` возвращает тот же meta-тег, который уже
   можно выводить на сайте через `NEXT_PUBLIC_GOOGLE_VERIFICATION` (см. ниже);
   если тег уже на проде, сразу `webResource().insert(verificationMethod=
   "META", body=...)` — подтверждение завершается без доп. шагов. Ресурс типа
   `sc-domain:` (голый домен) требует DNS TXT, а не meta — проще подтвердить
   URL-prefix версию (`https://domain/`), она покрывает тот же сайт для
   большинства целей (sitemap, inspection, indexing).
4. После `sites().add(siteUrl=url)` с ролью `siteOwner` — `sitemaps().submit()`
   и `urlInspection().index().inspect()` для статуса по конкретным URL работают
   сразу.
5. Indexing API (`urlNotifications().publish(body={"url":u,"type":
   "URL_UPDATED"})`) — это прямой запрос на обход для конкретных URL, ближайший
   доступный через API аналог кнопки «Запросить индексирование» в UI.

**Яндекс.Вебмастер API:** требует своё OAuth-приложение (Google client_secret
не годится, разные провайдеры). Создание приложения само — единственный шаг,
который нельзя обойти кликами «Разрешить»: на `oauth.yandex.ru/client/new`
нужно явно выбрать «Для доступа к API или отладки» (не «для авторизации
пользователей»), указать redirect URI, и в правах явно отметить пункты со
словом «Вебмастер» — форма по умолчанию может предложить не те права
(Директ/Диск/Почта), это нужно поправить вручную один раз. ClientID и
client_secret самого приложения — это НЕ пароль от аккаунта, их можно
принимать от владельца открытым текстом. После этого:
1. `POST oauth.yandex.ru/token` с `code` из redirect → `access_token` +
   `refresh_token` (токен живёт ~180 дней).
2. `GET api.webmaster.yandex.net/v4/user` → `user_id`.
3. `POST /v4/user/{uid}/hosts` с `{"host_url": "https://domain:443"}` чтобы
   добавить хост (формат `scheme:host:port`, НЕ голый URL с `https://`
   префиксом в host_id дальше).
4. `GET .../hosts/{host_id (url-encoded)}/verification` → список применимых
   методов (`META_TAG`, `HTML_FILE`, `DNS`); затем
   `POST .../verification?verification_type=HTML_FILE` (**query-параметр,
   НЕ JSON body** — передать его в body даёт `FIELD_VALIDATION_ERROR
   "This field is required"` даже когда поле присутствует; `requests`
   через `params=` работает). Ответ содержит `verification_uin` — положить
   файл `yandex_<uin>.html` с содержимым `<html>...<body>Verification:
   <uin></body></html>` (не голый текст — голый текст даёт
   `WRONG_HTML_PAGE_CONTENT`) в public/ и опубликовать.
5. Повторить тот же POST verification после деплоя файла → когда файл отдаёт
   200, статус переходит `IN_PROGRESS` → `VERIFIED` за секунды.
6. `.../user-added-sitemaps` (не `/sitemaps/user-added`) для отправки sitemap
   — может отвечать 504 несколько минут (иногда больше суток) сразу после
   верификации, пока Яндекс догружает хост в систему (`.../summary` отвечает
   `HOST_NOT_LOADED` тем же временем); это проходит само, повторить вызов
   позже, не считать provider-side задержку поводом переделывать запрос или
   обещать владельцу конкретный срок.

Коды верификации Google агент прописывает в Vercel env как
`NEXT_PUBLIC_GOOGLE_VERIFICATION` и `NEXT_PUBLIC_YANDEX_VERIFICATION`
(корневой layout выводит их через `metadata.verification`), делает редеплой
прода и проверяет наличие тега в HTML до подтверждения через API.

Индексация после отправки sitemap + запроса обхода — дни-недели; ускорить
дальше нельзя, конкретных сроков не обещать.

## IndexNow — автоматическое уведомление при каждом изменении контента

IndexNow (протокол, который Яндекс и Bing поддерживают официально) уведомляет
поисковик о новой/изменённой странице за минуты, а не ждёт очередного обхода
робота (может быть дни). Правильная точка интеграции — не разовый скрипт, а
хук в существующую функцию инвалидации кэша (`revalidatePath`), которая и так
зовётся из каждого Server Action после записи: туда же добавляется вызов
IndexNow, и дальше всё работает сама по себе на каждое будущее изменение.

1. Сгенерировать ключ (32 случайных символа a-zA-Z0-9), положить файл
   `public/<key>.txt` с содержимым = сам ключ (без переноса строки), добавить
   точный путь в auth middleware exceptions (та же ловушка, что для
   verification-файлов — см. выше).
2. **Слать на `https://api.indexnow.org/indexnow`, НЕ на
   `https://yandex.com/indexnow`.** Прямой яндексовский эндпоинт отвечал
   `403 Invalid key` даже с правильным ключом и файлом, отдающимся 200 по
   прямому curl — похоже на проблему инфраструктуры самого эндпоинта, а не
   ключа. `api.indexnow.org` — общая точка входа протокола (создана IndexNow
   Foundation), раздаёт запрос всем участникам (Яндекс, Bing, Seznam) одним
   вызовом и отвечала 200 сразу.
3. Формат запроса: `POST` с JSON `{host, key, keyLocation, urlList}` —
   `keyLocation` обязательно полный URL до файла ключа, не просто имя файла.
4. Это не гарантирует индексацию (как и любой другой сигнал) — только
   ускоряет обход; говорить владельцу именно так, не как «моментальную
   индексацию».

## Favicon в выдаче поиска (Google SERP favicon)

Google показывает иконку сайта рядом с URL в выдаче только если файл
содержит разрешение не менее 48×48 пикселей; при отсутствии — дефолтный
глобус-заменитель вместо лого, без каких-либо ошибок/предупреждений в консоли.
Недостатоцно `<link rel="icon">` с PNG/SVG — Next.js App Router особо отдаёт
`src/app/favicon.ico` как `/favicon.ico` вне зависимости от мета-тегов в `<head>`, и
иденно этот файл Google сверяет при выборе иконки. Если он только 16/32px —
заменить `.ico` с мульти-разрешением (`Image.save(..., format='ICO',
 sizes=[(16,16),(32,32),(48,48),(64,64),(128,128),(256,256)])` в Pillow — важно `sizes`
на самом `.save()`, не список отдельных изображений в `append_images` без `sizes` —
тогда сохраняется только первый размер). Google подтянет новую иконку в
выдаче не сразу после деплоя — это нормальный срок, как и легкая индексация выше.

## Google Analytics 4 и Яндекс.Метрика через API (без UI, без пароля)

Оба создаются тем же OAuth-паттерном, что Search Console (см. выше) — просто
нужны дополнительные scope/права у уже существующих OAuth-приложений.

**Google Analytics (GA4) Admin API:**
1. Добавить scope `https://www.googleapis.com/auth/analytics.edit` к
   существующему Google OAuth-потоку (не создавать новое приложение).
2. Включить `analyticsadmin.googleapis.com` через `serviceusage` (тем же
   способом, что остальные Google API, см. выше).
3. `GET /v1beta/accounts` — у аккаунта Google почти всегда уже есть хотя бы
   один Analytics-аккаунт даже без осознанной настройки (остаётся с любого
   прошлого продукта); использовать его как `parent`, не создавать новый.
4. `POST /v1beta/properties` с `parent`, `displayName`, `timeZone`,
   `currencyCode`, `industryCategory` — создаёт ресурс (property).
5. `POST /v1beta/properties/{id}/dataStreams` с `type: WEB_DATA_STREAM` и
   `webStreamData.defaultUri` — создаёт поток, ответ содержит `measurementId`
   (`G-XXXXXXX`) для вставки в код сайта.

**Яндекс.Метрика API:**
1. У существующего Яндекс OAuth-приложения (которое использовалось для
   Вебмастера) право «Яндекс.Метрика» НЕ входит в права по умолчанию и не
   видно в основном списке доступов на странице приложения — нужно открыть
   «Настройки» → «Доступ к данным» → поле «Название доступа» (это поле
   автоподсказки/поиска, не статичный список) и ввести туда «метрика», затем
   выбрать появившийся вариант и сохранить. После этого нужно заново пройти
   OAuth-согласие (новый код, новый обмен на токен) — права, добавленные в
   приложение, не применяются к уже выданным токенам.
2. `POST api-metrika.yandex.net/management/v1/counters` с телом
   `{"counter": {"name":..., "site":..., "type":"simple",
   "time_zone_name":...}}`. **Не передавать `code_options` или другие вложенные
   объекты дополнительно** — API Метрики несколько раз падало с
   `invalid_json`/`Could not read JSON` на лишних вложенных полях даже при
   валидном JSON; минимальный флэт-набор полей создаёт счётчик успешно, а
   `code_options` (webvisor/clickmap/track_hash) включается позже прямо в
   JS-коде счётчика на сайте (`ym(id, 'init', {...})`), не через API создания.
3. Оба счётчика (Метрика + GA4) ставятся ТОЛЬКО в layout публичного сайта,
   не в корневой layout всего приложения — иначе аналитика собирает данные
   с внутренних страниц CRM, где есть персональные данные сотрудников и
   клиентов.
