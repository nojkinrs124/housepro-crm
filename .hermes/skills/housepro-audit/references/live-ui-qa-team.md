# Живой UI-тест CRM командой агентов (оркестратор + исполнители)

Когда владелец просит «пройти весь путь пользователя», «прожать все кнопки»,
«найти все баги» или жалуется, что прошлый тест был поверхностным. Ожидание
владельца: агенты ВЖИВУЮ проходят сквозные сценарии в браузере, а оркестратор
перепроверяет их находки и оценивает качество их работы. Статический разбор кода
и «страница открылась» тестом не считаются.

## Порядок

1. **Стенд** (подготовка — `local-crm-testing.md`, раздел «Local isolated Supabase stack»), плюс:
   - сверь миграции репо с `supabase_migrations.schema_migrations` локальной базы
     и докати недостающие (`docker exec -i supabase_db_Claude psql -U postgres -v ON_ERROR_STOP=1 < file.sql`
     + insert версии) — стенд, поднятый несколько дней назад, отстаёт от main;
   - **отключи pg_cron в локальной базе** (`select cron.alter_job(jobid, active:=false) from cron.job`):
     `call_vercel_cron()` бьёт в боевой домен с секретом из vault, то есть локальный
     стенд дёргает боевые кроны;
   - перенеси справочные данные, без которых сценарии упираются в пустоту: тарифы
     (`service_plans`) и шаблоны документов (`document_templates` + файл в бакет
     `document-templates`) — читать с прода по REST с secret key (только GET), писать
     в локальный стек с service key, `organization_id` подменить на тестовую организацию;
     файл в Storage грузить с `Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document`
     (octet-stream бакет отклоняет 415);
   - снять дамп до теста: `docker exec supabase_db_Claude pg_dump -U postgres --data-only --schema=public -Fc > …/db-before-qa.dump`.
2. **Production-сборка вместо `next dev`** для команды агентов:
   `NEXT_DIST_DIR=.next-qa npx next build` → `next start -H 0.0.0.0 -p 3100` (env из
   `.env.e2e.branch`, без прокси). В dev каждая новая страница компилируется 15–60 с,
   и 6 параллельных агентов дерутся за компиляцию; `.next-qa/` добавить в `.gitignore`.
3. **Общие артефакты в репо** (`docs/qa/`):
   - `UI-E2E-TEST-PLAN.md` — методика: минимальный набор проверок на каждую форму
     (пустая отправка, счастливый путь со сверкой каждого поля, кривые значения,
     сохранность ввода после ошибки, обязательность, редактирование не обнуляет поля,
     удаление, двойной клик), на каждый список (фильтр ↔ SQL count, поиск, пустое
     состояние, ширины 1280/1440/1920, канбан), сквозные сценарии по всем четырём
     направлениям сделок + договоры всех типов + остальные разделы, жалобы владельца
     как обязательные регрессии, формат находки P0–P3 с доказательством;
   - `AGENT-CONTEXT.md` — один общий контекст для всех исполнителей: URL, хелперы,
     SQL только select, лог сервера, префикс `__smoke__ <ID>`, «отчёт пишется по ходу
     в `docs/qa/runs/<дата>/<ID>.md`», формат итогового ответа.
   Субагенты ничего не знают о разговоре — в каждую задачу: «прочитай AGENT-CONTEXT.md»
   + своя зона + дословные жалобы владельца по этой зоне + имя браузерной сессии.
4. **Хелперы** — `scripts/crm_login.py` (вход, `set_value`, `form_dump`, `errors_on_page`)
   и `scripts/docx_dump.mjs` (текст и вёрстка сформированного договора). Проверь их
   сам одним вызовом до раздачи задач.
5. **Раздача без пересечений** (6 исполнителей): A — главная воронка + все жалобы
   владельца; B — договоры всех типов, DOCX, платежи/график; C — управление;
   D — продажа + подбор/подборки; E — лиды/контакты/объекты/показы + отмена/откат;
   F — бухгалтерия, аналитика, настройки, навигация, канбаны всех разделов.
   Каждый со своим `session` браузера и своим префиксом записей.
6. **Пока исполнители работают** — сам разбери жалобы по коду, чтобы было с чем сверять
   их находки (гипотезы, не выводы).
7. **Приёмка:** каждую P0/P1 воспроизвести лично (DOM/SQL/лог); статус
   «подтверждено / не подтвердилось / не воспроизведено»; оценка каждого исполнителя
   по покрытию, точности и доказательности; сводка в `docs/qa/QA-REPORT-<дата>.md`
   (таблица P0–P3, что править — файл/компонент, что работает, что не проверено).

## Где искать причины типовых жалоб (проверенные места в коде)

- «Сформировался пустой бланк с именами» — у типа договора нет записи в
  `document_templates`, и `generateContractDocx` уходит в `generateBasicDocx`
  (встроенная заглушка: стороны, объект, даты, сумма, подписи — без текста договора).
  Сначала проверь, для каких `template_type` есть шаблоны.
- «Укажите положительное число» в договоре — общий примитив `optPositiveNum`
  (`src/lib/schemas/index.ts`) требует `> 0` для `amount`/`deposit`/`owner_fixed_amount`:
  `0` отклоняется, пустое проходит. Проверяй, сохраняется ли ввод формы после такой ошибки.
- Подстановка сторон/объекта/дат в договор из сделки — `contracts/new/page.tsx`
  (`dealDefaults`) и мастер «Оформить» (`complete-deal.actions.ts`); у партий
  `PartyContactSelect` с `key` по типу договора — смена типа перемонтирует выбор.
- Фильтры реестров — `useRegistryFilters` хранит выбор в localStorage, не в URL:
  фильтр «залипает» между заходами и не виден в адресе. Канбан — `KanbanBoard`,
  горизонтальный скролл у контейнера внизу доски, стрелок прокрутки нет.
