# Визуальный/брендовый аудит HousePro (сайт + CRM)

Процедура для задач «применить брендбук», «общий дизайн CRM», «проверить
отчёт/печать». Источник бренда: `~/projects/work-space/brand/BRANDBOOK.md`,
`DESIGN.md` (копия в репо). Работа в отдельной ветке, в `main` — только
через PR с одобрением владельца.

## 0. Крупный редизайн — сначала отдельная ветка и preview-сервер

Если владелец присылает скрин/референс другого сайта и говорит «такие
анимации/дизайн» — не меняй общие токены вслепую. Сначала сделай
2-3 тестовые страницы на моковых данных (путь виде `/preview-v2/<page>`, без
зависимости от боевой БД), добавив путь в `PUBLIC_PREFIXES` мидлвари, свой
добавочный CSS-файл (не трогать боевые токены `globals.css`) и свой `distDir`
(`NEXT_DIST_DIR=.next-preview2`) на своём порту (`next dev -p 3100`) — это не мешает
боевой dev-сервер владельца, если он уже занят на 3000. `.next-preview2/` сразу
в `.gitignore` рядом с `.next-smoke/`, иначе тысячи build-артефактов уйдут в
`git status`. Дай владельцу ссылку на LAN-IP:порт (не localhost — владелец
открывает со своего устройства) и давай сам потыкать, прежде чем тратить
раунды на перенос в боевые страницы. Только после явного «нравится» переноси
в общие токены/компоненты (см. §5б ниже про анимации) — и спрашивай отдельно
каждый изизменимый аспект («радиус нравится?» отдельно от «анимации
нравятся?») одним `clarify` с несколькими вопросами, не одним открытым
«понравилось?»: одобрение «мне всё нравится» после пилота может оказаться
только одним из нескольких аспектов (как и случилось в этой сессии: владелец
взял анимации/тени, но не округление).

## 1. Доступ к CRM и dev-сервер

Вход живого агента в CRM (панель, сессия, cookie), keep-alive до Supabase,
`allowedDevOrigins`, второй dev-сервер на своём `NEXT_DIST_DIR` — это окружение
именно этого сервера, а не проект: см. skill `housepro-ops` (он лежит вне
репозитория, потому что репозиторий публичный).

Правило проекта: браузером ходить только по хосту, который уже перечислен
в `next.config.ts` → `allowedDevOrigins`; при редиректе на `/login` сессия
перевыпускается, а не «чинится» код страницы.
## 3. Съёмка и замеры в браузере

- Вкладка может быть `visibilityState: hidden` → framer-motion/анимации не
  стартуют, элементы имеют ширину 0. Первым делом
  `cdp('Emulation.setFocusEmulationEnabled', enabled=True)`.
- Держи вызов коротким (≤4 страниц, одна ширина): длинные циклы рвут
  WebSocket демона. Отдельная `session=` даёт свежий браузер.
- `capture_screenshot()` почти всегда таймаутится (60s) на первой попытке
  сразу после навигации на новую страницу — вызови `ensure_real_tab()` и
  повтори `capture_screenshot()` ещё раз; это тот же паттерн разогрева
  демона, что и у `goto_url`, не повод чинить код страницы. Ожидай этого на
  КАЖДОЙ странице серии скриншотов, не только на первой.
- Скрывай dev-значок: `nextjs-portal{display:none!important}`.
- Скроллится `main`, а не `document` — для низа страницы `main.scrollTop`.
- Замер переполнения реестра:
  `box=table.parentElement; box.scrollWidth-box.clientWidth` + видимые `th`.
  Мерить на 1280 и 1440 (меню ~300 px → таблица ~944/1104 px) и 1920.
- Печать: `Emulation.setEmulatedMedia(media='print')` + `Page.printToPDF(printBackground=True, preferCSSPageSize=True)`, число страниц — по `/Type /Page`.

## 4. Разбор моделями

Скриншоты всех экранов (масштаб 0.55) + выдержка правил из `AGENTS.md` и
брендбука → двум-трём моделям через локальный пул (как подключить — skill
`housepro-ops`), параллельно. Формат: сильные стороны /
системные проблемы / быстрые победы / экран за экраном / план. Сводить в
`brand/review/crm/PLAN.md` только совпавшее или подтверждённое правилами.
После правок — пары ДО/ПОСЛЕ на проверку целей; «не выполнено» от модели
перепроверять через DOM/`getComputedStyle` (часто ложное). То же правило
действует и на САМ аудит, не только на проверку правок: любая находка
vision-модели в категории «горизонтальное переполнение» / «обрезанная
колонка» / «плавающий виджет-значок» обязана пройти DOM-проверку
(`scrollWidth > clientWidth` на реальных контейнерах, `elementFromPoint`)
до того как попасть в отчёт — модель систематически путает обрезку кадра
скриншота и артефакты dev-режима (Next.js badge) с реальными дефектами
вёрстки; на практике в одной сессии 2 из 2 такого рода находок оказались
ложными при проверке. Отдельно про доступность: «N изображений с `alt=""`»
почти всегда ложная находка — миниатюры галереи лежат внутри кнопок с
`aria-label` («Показать фото N») и по правилам a11y ДОЛЖНЫ быть декоративными,
а описательный `alt` есть у крупного кадра. Прежде чем записывать такой дефект,
открой компонент галереи и проверь, не обёрнут ли `<img>` в элемент с
подписью; счёт картинок на странице (`1 крупная + N миниатюр`) сам по себе
ничего не доказывает. Находку, которую vision-модель совпала с уже
независимо найденным через код/живое воспроизведение багом (например, то
же логическое противоречие статуса объекта) — отмечай как усиленное
подтверждение, а не отдельную находку.

## 5б. Просьба «анимации» ≠ смена радиуса/теней

Когда владелец просит «такие анимации» со скрина/референса (count-up
чисел, bounce при выборе, появление карточек в stagger, toast) — это
не закрывается добавлением `--hp-shadow`/`--hp-ease-*` токенов и `transition`
в CSS-классах — токены без React-состояния/JS-логики дают только hover-эффекты,
которые никто не задерживает, если навести мышь коротко. Само «мне нравится
анимации» без видимой разницы после пилота обычно значит: в компонентах
не портировались сами эффекты (count-up хук, stagger-задержка рендера, bounce
на `onClick`) — только общие токены. Добавляй их точейно в конкретные
компоненты (хук count-up на `requestAnimationFrame`, `style={{animation: '...
${index*0.05}s forwards'}}` для stagger, `animation: 'hp-bounce ...'` на
активном `style` при выборе чипа/вида), а не только в токены CSS.
Проверяй реальнюй эффект в браузере до ответа владельцу: для count-up
— сравни текст `.hp-price` вразряд коротких `sleep` сразу после `goto_url`
(должен меняться от 0 к финального), для hover/active — `getComputedStyle`, не только
наличие класса в JSX.

## 6. Подводные камни кода

- Строку-дату `YYYY-MM-DD` перед форматированием в поясе агентства превращай в
  `${d}T12:00:00Z` — полночь UTC сдвигается поясом на соседний день.
- Часть страниц `(dashboard)` сжата до отступа в 1 пробел: точная строковая
  замена из Python молча не находит фрагмент — ищи `grep -n` и заменяй
  регексом, нечувствительным к пробелам (`\s*`.join(re.escape(tok))), с
  `assert n` на число замен; после — `tsc` ловит недобавленные импорты.
- В JS-регексах `\b` не работает с кириллицей — границы задавай `(^|\s)`/`(\s|$)`;
  проверяй регекс в `node`, а не в Python.
- Массовая замена по `key: '<name>'` задевает конфиги фильтров
  (`{ key: 'type', options: ... }`) — искать по `key: '<name>', title:`.
- `write_file` по существующему файлу требует полного `read_file` в этой задаче.
- Перед коммитом: `npm run version:minor|patch` → `npm run check` (в фоне,
  notify) → `git add -A -- . ':!AGENTS.md'` → commit → `env -u HTTPS_PROXY -u HTTP_PROXY git push`.
- Правка, сделанная ПОКА `npm run check` уже идёт, им не покрыта (отпечаток
  считается по состоянию на старт) — после неё перезапусти check, и только
  его зелёный результат даёт право на коммит. То же с `npm run version:patch`:
  он меняет `package.json`, поэтому после подъёма версии check прогоняется
  заново, иначе гейт видит «другой код».
- Любая команда supabase CLI переписывает отслеживаемый `supabase/.temp/cli-latest`
  и он всплывает в `git status` — перед commit `git checkout -- supabase/.temp/cli-latest`,
  пока не решил осознанно коммитить эту строку.
- Когда браузер-демон флапает, фильтры/чипы страницы дешевле проверить по
  SSR-HTML: `curl -H "Cookie: ..." <url> -o page.html` + regex по `hp-chip`.
  Но элементы за клиентским переключателем вида (`usePersistedState`
  'cards'/'list'/'kanban') в этот HTML не попадают — отсутствие колонки
  реестра в разметке НЕ значит, что её нет: переключи вид в браузере
  (клик по кнопке вида) и только тогда читай `thead th`.
