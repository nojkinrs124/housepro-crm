# Аудит HousePro CRM

## When to Use

Когда применять: «проверь всё», «найди баги», «пройди весь путь», «аудит UI»,
«почему цифры не сходятся», «применить брендбук». Не начинать с правок кода и не
считать зелёный build доказательством работоспособности.

## Порядок

1. **Границы и разрешения.** Подтвердить домен/репозиторий, отдельно спросить про
   мутации. Без явного разрешения прод — read-only: не создавать, не менять, не
   удалять, не запускать рассылки/вебхуки. Динамика — на локальном стенде
   (`housepro-local-testing`).
2. **Исходное состояние.** `git status --short --branch`, проектные правила и
   актуальные audit/бэклог-документы, полный гейт до исследования. Зелёный гейт
   значит только то, что зелёные эти проверки.
3. **Карта покрытия.** Сайт и CRM по ролям/разделам, сущности и потоки, действия,
   автоматизации, права, адаптивность. Для каждого сценария: не проверено /
   статически / в браузере / заблокировано + среда.
4. **Параллельные домены — только независимые** (безопасность, бизнес-процессы,
   UI/UX) через `delegate_task`, каждому — область и запрет на запись. Выводы
   субагентов — гипотезы: каждую находку P0/P1 перепроверить лично по коду,
   тестом или воспроизведением, зафиксировать `путь:строка` либо URL/шаги.
5. **Безопасный динамический тест.** Локальный стенд, записи с уникальным маркером,
   интеграции замоканы, заранее определена очистка. Не доказана изоляция — только
   статический анализ. Рецепт стенда и RLS-проверки — `housepro-local-testing`.
6. **Отчёт разделяет доказательства и пробелы.** Приоритет, область, шаги,
   ожидаемое/фактическое, источник доказательства, статус проверки. Отдельно —
   что не проверено и какие блокеры. Сначала план владельцу, масштабные правки —
   только после согласования объёма.
7. **UI — отдельный проход.** Скриншоты ключевых экранов → `vision_analyze` на
   каждый → для находок «переполнение/обрезка/плавающий элемент» DOM-проверка
   перед включением в отчёт. UI-находки — в отдельный файл
   (`docs/UI-AUDIT-<дата>.md`), не в тот же поток, что функциональные.
8. **Живой тест «путём пользователя»** — когда просят «прожать все кнопки» или
   прошлый тест пропустил очевидное. Только сквозной проход формы с перечитыванием
   сохранённого состояния ловит сброс формы, не подтянувшиеся стороны, пустой DOCX.
   Порядок и роли — `references/live-ui-qa-team.md`.
9. **Свод в один документ.** Все домены в одном файле с таблицей P0/P1/P2 и
   пометкой источника на каждую находку (воспроизведено живьём / DOM-подтверждено /
   статический анализ / НЕ подтвердилось). Отклонённые гипотезы оставлять с
   пометкой — следующая сессия не должна проверять их заново.

## Роли-аудиторы (чек-листы для `delegate_task`)

Каждая роль — только чтение, отчёт в файл, без правок.

**UX-потоки.** Восстановить реальные сценарии по коду и посчитать шаги от
`/dashboard`: (1) записать позвонившего клиента, (2) завести по нему сделку,
(3) продвинуть сделку по стадии, (4) поставить и закрыть задачу, (5) добавить
объект, (6) найти контакт/объект, (7) сгенерировать договор, (8) провести платёж,
(9) записать показ. Искать: путь длиннее трёх шагов, тупики (создал контакт — а
сделку только из другого раздела), лишние подтверждения обратимых действий,
дубли путей к одному действию.

**Тексты интерфейса.** Жаргон из БД (`deal_stage`, `null`, `undefined`, `0` вместо
«не указано»), англицизмы при наличии русского слова, бесполезные ошибки
(«Что-то пошло не так», текст исключения Supabase/Zod), разнобой терминов
(клиент/контакт/заказчик), неинформативные кнопки, пустые состояния без подсказки,
подтверждения без последствий, канцелярит и обвинение пользователя.

**Консистентность UI.** Инвентарь по каждому модулю: списки (таблица/карточки/
канбан, где фильтры и поиск), формы (модалка/страница, сколько полей, где кнопка),
кнопки (сколько первичных, как подписаны одинаковые действия), карточка записи,
обратная связь (toast/баннер/инлайн), пустые состояния, загрузка, подтверждения.
Эталон — самый частый вариант; остальное — расхождение.

**Схема БД.** Таблицы без `.from()`, колонки без чтения/записи, колонки
«пишутся, но не читаются», `NOT NULL` без дефолта, дубли полей, неиспользуемые
функции/триггеры/индексы/вьюхи, енумы со значениями вне кода, легаси `clients`/
`owners`, поля форм, которые ни на что не влияют. Без доступа к базе выводы
помечать как требующие проверки живыми данными.

**Мёртвый код.** Позиция «мёртвое» только если: `grep` не находит импортов; нет
динамических обращений по строке; это не `page`/`layout`/`route.ts`; не точка
входа скрипта/воркфлоу/Edge Function/триггера; не экспорт публичного API. Иначе —
«подозрения» отдельным списком.

## Проверки, которые ловят реальные баги

- **«Цифры врут»** — не читать код «на глаз»: вытянуть те же таблицы через
  Supabase REST и в Python повторить **точно ту же** цепочку, что страница
  (`computeKpis`/`toPaymentStatus`/`isAgencyRevenue`, расчёт диапазона дат).
  Несколько денежных KPI рядом почти всегда считаются по разным формулам
  (доход агентства vs объём сделок vs все платежи) — расхождение между ними не баг.
  Совпало с UI, а ощущение осталось → подозревать данные (массовые `completed` без
  `paid_at` с одинаковым `created_at`, авто-график на год вперёд).
- **Денежная колонка с условным источником** (`if scheme === X then fieldA else fieldB`)
  — проверить, что каждая ветка семантически означает то же, что заголовок.
  Реальная находка: «Вознагр.» при фиксированной схеме показывала выплату
  собственнику, а не комиссию агентства.
- **Чек-лист готовности** может лгать из-за узкого `select()`: `checkProperty()`
  получает `undefined` и вечно показывает предупреждение. Сверять `select()`-строку
  с интерфейсом чекера, а не считать это рассинхроном данных.
- **Кнопка «Исправить»** может чинить только одно из двух направлений
  двустороннего рассинхрона, который сама же показывает. Прочитать условие внутри
  Server Action и сверить с обоими условиями показа в `readiness.ts`.
- **Тихий no-op** в `advanceDealStage`/`stageForMilestone`: если целевая стадия не
  позже текущей, функция делает `return` — тест ничего не проверяет, пока запись не
  продвинута ровно перед целевой.
- **Формат/вид**: факт (цвет, текст бейджа, `border-radius`, тень, позиция) —
  только через `getComputedStyle`/DOM. Vision-модели путают оттенки и форму углов и
  уверенно заявляют несовпадение там, где числа идентичны. Тёмный кружок с буквой в
  углу на dev-скриншоте — индикатор Next.js Dev Tools, не элемент CRM.

## Визуальный/брендовый аудит

Полная процедура — `references/brand-visual-audit.md`: вход в CRM без пароля в чате,
съёмка экранов, замеры переполнения, разбор несколькими моделями, правила бренда v2,
проверенные паттерны правок. Правила, которые действуют всегда:

- Бренд-решения владельца не пересматривать: «ХаусПро» + «Руслан Ножкин», тексты от
  «я», «от 10%» за управление, латунь только на лесном фоне; статусные цвета
  (good/warn/danger/info) — язык CRM, на сайте их нет.
- Радиус/тень/motion — **три независимых токена** (`--hp-radius*`, `--hp-shadow`,
  `--hp-ease-*`). Владелец может одобрить анимации и отменить округление; откат
  одной оси — правка одной переменной. Текущие значения — в `globals.css`, не в
  документе.
- Меняешь токены — синхронно правь `RULES` в `scripts/checks/design-tokens.mjs`
  (массив кодирует старые запреты) и переснимай baseline, иначе гейт красный на
  коде, который владелец сам одобрил.
- В CRM цвет несёт статус, а не раздел: нормальное состояние — нейтральный бейдж.
- Иконки `lucide-react` — `strokeWidth={1.6}` на каждой; проверять DOM-подсчётом
  `svg[stroke-width]`, не на глаз. Проп `title` иконкам не передаётся — оборачивать
  в `<span title="…">`.
- Реестры не скроллятся вбок на 1280/1440: второстепенные колонки — `hideBelow`,
  действия строки — меню «…». Одна канбан-доска на экран, направления — вкладками.
- Документы собственнику не утверждают того, чего CRM не знает (коммуналка зависит
  от объекта; счета ЖКХ платит собственник). Словарь — «Вознаграждение
  управляющего», не «Удержание агентства»; правя подпись строки расчёта, править и
  unit-тесты, которые ищут её по тексту.

## После аудита

Перед исправлениями прочитать `AGENTS.md` и `docs/IMPROVEMENTS.md`, убедиться что
`npm run check` зелёный **до** правок, дальше — по одному согласованному шагу с
прогоном проверок после каждого. Пакет правок фиксируется в репозитории:
`docs/audit-remediation/PATCHLOG.md` (причина → изменение → как проверено → риск) и
`TEST_REPORT.md` (что реально прогнано, что `NOT RUN`), в самом отчёте аудита у
находки проставляется статус и версия.
