# HousePro — слияние ветки и выкладка

Применяется, когда план правок закрыт и владелец сказал «выкатывай».

## 1. Проверить расхождение с main до PR

```bash
env -u HTTPS_PROXY -u HTTP_PROXY git fetch -q origin main
git rev-list --count origin/main..HEAD   # сколько своих коммитов
git rev-list --count HEAD..origin/main   # 0 → конфликтов не будет
```

PR создавать с телом из файла, а не одной строкой:
`gh pr create --base main --head "$(git rev-parse --abbrev-ref HEAD)" --title ... --body-file "$TMPDIR/pr.md"`.
В теле — что изменилось по версиям и на каком коммите зелёный `npm run check`.

## 1б. Чужие коммиты в ветке: не сливать свой фикс вместе с ними

Ветка может быть общей: над проектом параллельно работает второй агент или
сам владелец. Поэтому перед пушем и перед PR всегда смотри, что в ветке
кроме твоего:

```bash
git log --format="%h %ad %s" --date=iso origin/main..HEAD | cat
git show --stat <чужой-sha> | head -20
```

Признаки чужой работы: коммит, которого ты не делал, по времени между твоими;
`package.json` с версией выше той, что ты только что ставил (другой агент тоже
вызвал `npm run version:*`, из-за чего твой коммит с меньшей версией оказался
позже по времени); правки файлов вне твоей задачи. `gh pr create` в ответ
«a pull request for branch X already exists» — тоже сигнал: открой PR и
сверь title/author, он может быть не твой.

Не сливай смешанный PR и не чини чужое. Останови выкладку, назови владельцу
чужой коммит и спроси, что выкладывать. Типичный ответ — «свои доработки
выкладывай, второй агент работает над X», и дальше:

```bash
git checkout -b <своя-тема> origin/main
git cherry-pick <свой-sha>          # только свои коммиты
git diff --stat HEAD~1              # убедись: только твои файлы
npm run version:patch && git commit -q --amend --no-edit
```

Версию после cherry-pick ставь заново: номер из общей ветки принадлежит
чужому коммиту. Затем `npm run check` и отдельный PR от `main` — так твой
фикс выкладывается независимо, а чужой PR остаётся его автору.

## 2. Красный CI: сначала выяснить, чей он

Перед тем как чинить или блокировать слияние, сравни тот же чек на HEAD
`origin/main`: падение может быть унаследованным, а не твоим.

```bash
gh api repos/<owner>/<repo>/commits/<sha>/check-runs -q '.check_runs[] | "\(.name) \(.conclusion)"'
J=$(gh api repos/<owner>/<repo>/commits/<sha>/check-runs -q '.check_runs[] | select(.name=="ci") | .id')
gh api repos/<owner>/<repo>/actions/jobs/$J/logs | grep -E "FAIL |×| Tests |timed out"
```

Если те же тесты падают и на нескольких предыдущих коммитах `main`, а локально
проходят несколько прогонов подряд — это флапающие тесты раннера (в HousePro
это серверные экшены с таймаутом 5 с), а не регрессия ветки: сливать можно,
но сказать владельцу, что чек красный и почему. Чинить чужой флап внутри
бренд-PR не нужно — это отдельная задача.

`gh` в этой сборке не знает `gh pr checks --watch` и `gh run list --branch` —
опрашивай циклом:

```bash
for i in $(seq 1 25); do out=$(gh pr checks <N> 2>&1); \
  echo "$out" | grep "^ci" | grep -qE "pending|queued|in_progress" || break; sleep 20; done
echo "$out"
```

Запросы к api.github.com иногда отваливаются по `TLS handshake timeout` —
повтори вызов 2–3 раза, прежде чем считать это ошибкой доступа.

## 3. После слияния

- Дождись статуса Vercel на merge-коммите:
  `gh api repos/<owner>/<repo>/commits/<sha>/status -q '.statuses[] | select(.context|test("Vercel")) | .state'`.
- Проверь именно тот адрес, который реально обслуживает прод, и скажи
  владельцу его. Домен из названия проекта может быть не подключён.

## 4. Подключение домена (Vercel + Reg.ru)

Доступы — записи панели «Vercel API» (токен в secret) и «Reg.ru» (логин + пароль).
Как читать секреты (`secret-run.sh`, сброс `SECRET_FIELD` во вложенном вызове)
и что значит «Панель заблокирована» — skill `housepro-ops`.

Токен проверяй до любых изменений:

```bash
curl -s -H "Authorization: Bearer $V" https://api.vercel.com/v2/user
```

`{"error":{"code":"forbidden","invalidToken":true}}` → токен не тот/отозван:
не перебирай эндпоинты. Просьбу формулируй со ссылкой и названием раздела
целиком: https://vercel.com/account/settings/tokens → Create Token, scope —
команда владельца. Простое «создай токен в Vercel» уводит в Team Settings
→ Key Management (KMS-issuer для подписи JWT) — похоже называется, но не даёт
токена к REST API. Если пришли скриншот/ключ из KMS — скажи, что это другая
сущность, и дай точный путь. Значение токена в чат не принимать и не печатать
(`len`, `isalnum` — максимум диагностики).

Целевая конфигурация, которую согласовал владелец: основной домен без `www`,
`www` редиректит на него.

### Порядок (проверено)

1. Домены в проект: `POST /v10/projects/<id>/domains` с `{"name":"<домен>"}`
   для апекса и для `www` (id — из `GET /v9/projects?limit=20`).
2. Редирект: `PATCH /v9/projects/<id>/domains/www.<домен>` с
   `{"redirect":"<домен>","redirectStatusCode":308}`. Это свойство домена в
   проекте, а не DNS-запись, — в зоне `www` остаётся CNAME на Vercel.
3. DNS у регистратора: A `@` → `76.76.21.21`, CNAME `www` →
   `cname.vercel-dns.com.`; старые записи парковки регистратора сначала
   удалить, иначе апекс будет отдавать два A-адреса.
4. Сертификат не запрашивай вручную: `POST /v5/certs` отвечает `forbidden`
   для домена проекта — Vercel выпускает Let's Encrypt сам по `http-01`
   в течение пары минут после того, как A-запись начала отвечать.
   Готовность конфигурации — `GET /v6/domains/<домен>/config`:
   `misconfigured:false` + `configuredBy: A|CNAME`.

### Reg.ru API2

Эндпоинт `https://api.reg.ru/api/regru2/<команда>`, параметры формой:
`username`, `password`, `output_format=json`.

- `ACCESS_DENIED_FROM_IP` — не неверный пароль: в Reg.ru нужно включить доступ
  к API и внести IP сервера в белый список (свой IP — `curl https://api.ipify.org`).
  Смена IP сервера снова ломает доступ.
- Домен передаётся как `dname=<домен>`. JSON-массив `domains=[{"dname":...}]`
  из документации даёт `NO_DOMAIN: domain_name not given or empty`.
- Команды: `zone/get_resource_records`, `zone/add_alias` (A, параметр
  `ipaddr`), `zone/add_cname` (параметр `canonical_name`), `zone/remove_record`
  (`subdomain` + `record_type` + `content`).
- Внешний `result:"success"` ещё не значит успех: результат операции лежит
  в `answer.domains[].result`, ошибка — там же в `error_code`. Проверяй
  вложенный уровень, иначе «успешно» вернётся на отклонённую правку.

## 5. Миграции и секреты без локального доступа (Supabase MCP + Vercel API)

Когда задача не требует полного локального стенда (п.6 `local-crm-testing.md`) —
точечная миграция схемы или ротация секрета прямо на проде через коннекторы:

- **Миграция схемы**: `connectors__supabase__APPLY_A_MIGRATION` с `ref` проекта
  (не путать с именем репозитория — `ref` это Reference ID из Project Settings).
  Применяется сразу на прод-БД, минуя `npx supabase`/локальный стек — нормально
  для аддитивных миграций (новые таблицы/колонки/индексы), которые проходят и
  через `guard-migration` (не DROP). После миграции обязательно перегенерировать
  типы: `connectors__supabase__GENERATE_TYPESCRIPT_TYPES` возвращает полный файл —
  писать его целиком в `src/types/supabase.ts` (большой ответ уходит в spillover-файл,
  читать его через `execute_code`/`read_file`, не пытаться распечатать в чат).
  Проверить, что типы реально обновились: `git diff --stat src/types/supabase.ts`
  должен показать новую таблицу/колонку, а не 0 изменений.
- **Ротация секрета, используемого и в Vercel env, и в Supabase Vault одновременно**
  (например `CRON_SECRET` / `channel_cron_secret`): генерировать ОДНО значение,
  писать в оба места тем же вызовом раунда — PATCH `/v9/projects/<id>/env/<envId>`
  в Vercel (найти `envId` через `GET /v9/projects/<id>/env`, искать по `key`) и
  `select vault.update_secret((select id from vault.secrets where name='<имя>'), '<значение>')`
  через `APPLY_A_MIGRATION` в Supabase. **Vercel env переменная не применяется к уже
  работающим serverless-функциям без нового деплоя** — после PATCH нужен redeploy:
  `POST /v13/deployments?forceNew=1` с `{"name":"<project>","deploymentId":"<текущий>","target":"production"}`,
  дождаться `readyState:"READY"` через `GET /v13/deployments/<id>`, и только тогда
  проверять функциональность. Переменная с `"type":"sensitive"` никогда не отдаёт
  значение обратно (`decrypted:false` всегда) — ротацию проверяй через реальный вызов
  эндпоинта, не через повторное чтение переменной.
- **Проект в Vercel может называться не как репозиторий на GitHub** (репозиторий
  `housepro-crm`, проект в Vercel — `housepro24`) — искать по `GET /v9/projects` и
  сверять по `id`/алиасам домена, не угадывать slug по названию репо.
- **pg_cron-функция, которая дёргает собственный прод через `net.http_get`, должна
  бить прямо в кастомный домен, а не в `<project>.vercel.app`.** Если у проекта
  настроен кастомный домен, `*.vercel.app` обычно отдаёт 308-редирект на него — а
  `pg_net` (как и большинство HTTP-клиентов) НЕ переносит заголовок `Authorization`
  через межхостовый редирект, так что финальный запрос к кастомному домену приходит
  без Bearer-токена и получает честный 401. Симптом сбивает с толку: ручной `curl`
  с тем же секретом прямо на кастомный домен отвечает 200, а автоматический прогон
  pg_cron на тот же эндпоинт — 401; разница в том, что ручной тест и автоматический
  вызов на самом деле бьют в разные URL. Диагностика — прочитать тело функции
  (`select pg_get_functiondef('public.<fn>(...)'::regprocedure)`), проверить, какой
  именно `url` она строит, и воспроизвести тот же редирект отдельным `curl -L` с
  заголовком — 401 после редиректа при 200 на прямой URL подтверждает причину.
  Фикс — захардкодить в функции кастомный домен, а не домен проекта.

### Проверка, не дожидаясь DNS

У публичных резолверов TTL старой записи может быть часами, поэтому «домен
ещё отдаёт парковку» — не признак ошибки настройки. Разделяй два вопроса:

```bash
dig +short @ns1.reg.ru <домен> A          # что отдаёт авторитетный сервер зоны
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" \
  --resolve <домен>:443:76.76.21.21 https://<домен>/   # хостинг, минуя кэш
```

`--resolve` на 443 даёт `000`, пока сертификат не выпущен, а на 80 уже
отвечает 200 — это нормальное промежуточное состояние, подожди и повтори.
Проверяй так же `www` (ожидается 308 на апекс), `http` → `https` и вход в
CRM. Владельцу отдельно скажи, что у него в браузере ещё может открываться
страница регистратора из кэша DNS (до суток), и как проверить раньше —
инкогнито или мобильный интернет.
