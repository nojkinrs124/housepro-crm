# Локальный стенд и живые проверки HousePro

## When to Use

Когда применять: нужен живой прогон формы/сценария, проверка RLS вторым
пользователем, воспроизведение сбоя записи — то есть всё, что нельзя делать на
проде. Полная процедура с командами — `references/local-crm-testing.md`.

## Варианты среды (выбирать по риску)

| Что проверяем | Среда |
|---|---|
| Открыть экран, посмотреть вёрстку, пройти форму без записи | dev-сервер против боевого Supabase, только чтение |
| Создать/удалить запись, сломать данные | локальный изолированный стек `npx supabase start` |
| RLS и мультиарендность | локальный стек + второй org и пользователь |
| Денежные сценарии, кроны | локальный стек + отключённые pg_cron-джобы |

## Ключевые грабли (из практики, не теории)

- **Keep-alive к Supabase висит минутами** — dev-сервер поднимать с preload
  preload из skill `housepro-ops`, иначе страница открывается 3-5 минут. Прод не затронут.
- **Сессия CRM короткая** (JWT ~1 час, плюс idle-logout ~10 минут): держать готовый
  сниппет повторного логина целиком и перезапускать его при любом редиректе на
  `/login` до многошаговой формы. Пароль писать только в scratch-файл, не в `/tmp`
  и не в чат.
- **Скрытая вкладка** (`visibilityState: hidden`) → анимации не играют, таблицы
  меряются нулём, Suspense-скелетон не резолвится. Перед замерами:
  `Emulation.setFocusEmulationEnabled`.
- **`allowedDevOrigins` в `next.config.ts`** — это не мелочь HMR: хост не из списка
  оставляет `LoginGate` в вечном `animate-pulse` без ошибки в консоли. Открывать
  через хост, который там уже есть, а не `127.0.0.1` по привычке.
- **Два dev-сервера — только с разными `NEXT_DIST_DIR`** и портом; новый dist-каталог
  сразу в `.gitignore`, иначе сотни чанков уедут в `git add -A`.
- **Playwright headless здесь не запускается** (нет libasound, нужен sudo) — не
  тратить раунды, мерить через DOM.
- **`<select>`: `value` не из `<option>` молча не применяется**; `type="number"` вне
  `min`/`max` блокирует submit без единого сообщения. Проверять `checkValidity()` и
  реальные значения опций, а не «фильтр не работает».
- **React 19 `<form action>`** сбрасывает неконтролируемые поля после неудачного
  сабмита — сравнивать `form_dump()` до/после, иначе «данные не сохранились» спишется
  на сервер.

## Поиск багов, которые не видны в UI

- **`redirect()` после непроверенного `.update()`** — самый опасный класс тихого
  провала: пользователь видит успешный переход, а запись осталась в старом статусе.
  Массовый запрос для аудита:
  `grep -rn "redirect(" src/features/*/actions/*.actions.ts -B5` — между
  `insert`/`update` и `redirect()` должен быть `if (error) return`.
- Проверять не только `error`, но и «ноль затронутых строк»: `.update().select().maybeSingle()`
  при пустом результате отдаёт `error = null`. Условие провала — `error || !data`.
- Сбой записи воспроизводить временным триггером на конкретный `id`, снимать его
  сразу после теста.
- Каждый тестовый объект помечать литералом (`__smoke__`) — потом удаляется одним
  запросом, без риска задеть боевые строки.
- **Отключать pg_cron на локальном стенде**: `call_vercel_cron()` бьёт в боевой
  домен, и локальный стенд начнёт дёргать прод-кроны.

## Правила

- Мутации на боевой организации — только по явному разрешению владельца и с
  заранее описанной очисткой; бэкап изменяемых строк — в репозиторий, не в `/tmp`.
- Тестовый админ `audit-admin@housepro.local` (id `38593b6c-9f2b-4b14-a4de-3e494c4fe68c`)
  живёт в боевой организации по разрешению владельца — не удалять.
- Ключи Supabase и доступы — skill `housepro-ops` (вне репозитория), значения не печатать.
