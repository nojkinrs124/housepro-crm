# Local HousePro CRM testing (agent login, dev server, browser)

Repo: ~/projects/work-space/housepro-crm. Work in a dedicated branch; never merge to `main` without owner PR approval. Before push: `npm run version:minor|patch` + `npm run check` (run check in background, ~3 min). Commit everything with plain `git add -A` (AGENTS.md is the project rules file now and is committed with the work, not excluded). Network commands need `env -u HTTPS_PROXY -u HTTP_PROXY`.

## Browser checks
- The browser tool tab is often `visibilityState: hidden` → framer-motion entrance animations don't run and tables measure width 0. Call `cdp('Emulation.setFocusEmulationEnabled', enabled=True)` first.
- Browser daemon times out on long loops and on screenshots: one or a few pages per call, prefer DOM measurements (scrollWidth vs clientWidth, computed styles) over screenshots. Use a named session (e.g. `crm2`).
- Playwright headless can't launch here (missing libasound, needs sudo) — don't try.
- Hide the Next dev badge: inject style `nextjs-portal{display:none!important}`.
- `goto_url`/`new_tab` can throw `Page.navigate timed out after 5s` right after the browser daemon just restarted or after a long idle gap — call `ensure_real_tab()` once and retry the same `goto_url`, this is a daemon-warmup race, not a broken page.
- Session cookies expire mid-audit (short JWT TTL) and silently redirect back to the role-picker login screen. Keep one reusable re-login snippet ready (click "Я сотрудник" → click "Вход по email и паролю" → fill email → fill password → click "Войти" → sleep 3-4s → verify via textContent) and re-run it whole on any unexpected redirect to `/login`, rather than re-discovering the role-picker click each time. The dashboard also has a client-side idle logout (~10 min without input events): a JS-driven browser session that only reads pages counts as idle, so the next submit lands on `/login` with the form lost — re-login right before any multi-step form sequence. The helper `~/.hermes/cache/scratch/qa/crm_login.py` (`crm_login(path)`, `set_value`, `form_dump`, `errors_on_page`) does this for the local stand.
- Server-action forms here may render their error banner at the top of the form while the page stays scrolled at the submit button: measure the banner's `getBoundingClientRect().top` — a large negative value means the user never sees the error. Also diff `form_dump()` before/after a failed submit: React 19 `<form action>` resets uncontrolled inputs (`defaultValue`) after the action returns, so every failed validation wipes the form unless fields are controlled or values are echoed back.

## Code pitfalls found
- Constants exported from a `'use client'` module arrive empty in server components (lost StatStrip labels) — put shared constants in a plain module.
- Tailwind `-z-10` child inside a link without `isolate` disappears under the parent background (sidebar active highlight).
- JS regex `\b` does not work with Cyrillic — use whitespace/edge boundaries.
- Registry tables live in `overflow-hidden/overflow-x-auto`; dropdown menus must portal to body with `position: fixed`.
- Many files use 1-space indentation after compaction — prefer whitespace-insensitive regex edits or the patch tool.

## Local isolated Supabase stack (for destructive/dynamic testing)

When the owner allows creating/deleting test records but a production org must stay untouched, stand up a fully isolated local stack instead of testing against production data — this repo already ships the tooling for it.

1. **Install Docker if missing** (если sudo спрашивает пароль — поставить docker вручную): `sudo apt-get install -y docker.io docker-compose-v2 && sudo systemctl enable --now docker`. One-shot `npx supabase` commands need `sudo env PATH="$PATH" npx supabase ...` since the daemon runs as root.
2. **Start the stack with slow-network exclusions.** `npx supabase start` on a slow/flaky network link reliably fails pulling `logflare`/`vector`/`imgproxy` images (ECR timeouts) and the CLI prunes everything and exits non-zero. Exclude them from the first attempt: `sudo env PATH="$PATH" npx supabase start -x logflare,vector,imgproxy` (background=true, can take 10+ min on a slow link — poll `sudo docker ps` and the log file, don't assume failure before checking both). The exact container name is `logflare`, not `analytics` — using the wrong name makes the CLI reject the whole `-x` list and fall through to the slow path.
3. **Wire env + seed**: `node scripts/e2e/write-branch-env.mjs` (writes `.env.e2e.branch` from `supabase status`) → `node e2e/seed-cli.ts` (idempotent; creates org + `smoke@housepro.local` / `smoke-Pass-2026`). `npx supabase start` applies `supabase/migrations/*` automatically — no separate migrate step needed.
4. **Run the CRM against it**: `source .env.e2e.branch && env -u HTTPS_PROXY -u HTTP_PROXY NEXT_DIST_DIR=.next-smoke npx next dev -p 3100` (background=true). If port 3100 is already held by a stale process: `sudo fuser -k 3100/tcp` first.
   For multi-agent QA serve a production build instead: `set -a; source .env.e2e.branch; set +a; NEXT_DIST_DIR=.next-qa npx next build` then `NEXT_DIST_DIR=.next-qa npx next start -H 0.0.0.0 -p 3100` (background), open via `http://<lan-ip>:3100`. Dev compiles each route on first hit and parallel agents turn that into timeouts. Add the dist dir to `.gitignore`. A `next-server` process left from an older run may hold no port but keep running — check `ss -ltnp | grep 3100`, not `ps`.
4a. **Bring an existing stack up to date before testing.** Compare `ls supabase/migrations` with `select version from supabase_migrations.schema_migrations`; apply missing files with `docker exec -i supabase_db_Claude psql -U postgres < file` and insert the version row. Then disable pg_cron jobs (`select cron.alter_job(jobid, active:=false) from cron.job`) — `call_vercel_cron()` targets the production domain, so a running local stack fires real prod cron endpoints.
4b. **Reference data the seed lacks**: tariffs (`service_plans`) and document templates exist only in prod. Copy them via prod REST with the secret key (`~/.hermes/agent-secrets/supabase-housepro-keys.json`, entry `type=secret`) into the local org; upload template files to local storage bucket `document-templates` with `Content-Type: application/vnd.openxmlformats-officedocument.wordprocessingml.document` (octet-stream is rejected 415). **Upload under `templates/<USER_ID>/...` (the uploading staff user's id, as in prod), not `<ORG_ID>`** — the storage RLS policy matches `foldername(name)[2]` against `organization_members.user_id`, so an org-id folder makes generation fail with «Не удалось загрузить шаблон» while a service-key download of the same file returns 200 (a stand artifact, not a product bug). Without templates, contract generation silently falls back to the built-in stub in `generate.actions.ts` (parties + amounts only, no contract text) — that is the "blank with names" symptom. Verify by generating one document yourself before handing the stand to anyone.
4c. **Per-agent fixtures**: insert contacts (owner/tenant with passport + address, legal entity with requisites) and properties with `photo_urls` + `site_publish=true` directly in SQL, so deal stages "Подготовка/Показы" preconditions pass. `pg_dump --data-only -Fc` before the run for reset.
5. **Multi-org RLS testing**: create a second org + user directly in the local DB (GoTrue admin API for the auth user, then insert into `public.users`/`organization_members`) rather than through the UI signup flow, which requires email confirmation plumbing. The `users_guard_privileged_columns` trigger blocks changing `organization_id`/`role` for anyone except `service_role`/org-admin — as plain `postgres` superuser you must `alter table public.users disable trigger users_guard_privileged_columns;` around the UPDATE, then re-enable it. A fresh org also needs `onboarding_completed=true` set directly in SQL or every page redirects to `/onboarding`.
6. **Probe RLS directly with PostgREST + JWT, not just through the UI.** A blank/empty page under a second-org session is ambiguous (could be `notFound()`, could be a client-render glitch — see the Suspense-skeleton pitfall above). Get a real JWT (`POST /auth/v1/token?grant_type=password` with the anon key) and hit PostgREST directly: `GET/PATCH/DELETE http://127.0.0.1:54321/rest/v1/<table>?id=eq.<id>` with `apikey`/`Authorization: Bearer <jwt>`. An empty `[]` result with HTTP 200 on PATCH/DELETE (not a 403) is the normal RLS-filtered-no-match response — it means zero rows matched the policy, not that the request errored; confirm by re-reading the row as `postgres` superuser afterward to prove it is unchanged.
7. **To provoke a genuine server-side write failure** (for testing whether an action/automation checks `{error}` from a Supabase `.update()`), add a throwaway trigger that raises on UPDATE for one specific row id, drive the real user flow through the UI, then drop the trigger immediately after: `create function smoke_block_x() returns trigger as $$ begin if OLD.id = '<id>' and NEW.<col> is distinct from OLD.<col> then raise exception 'smoke_test: ...'; end if; return NEW; end; $$ language plpgsql; create trigger smoke_block_x_trigger before update on <table> for each row execute function smoke_block_x();` — disable/re-enable it (`alter table ... disable/enable trigger ...`) around any setup writes to the same row that must succeed first. Clean up both trigger and function when done; never leave a raising trigger in a stack meant to keep working.
8. **Clean up test data with a unique marker**: prefix every test record's name with the same literal (e.g. `__smoke__`) so it is trivially greppable for a later bulk delete, and never touch rows without that marker.
9. **A Server Action that `redirect()`s unconditionally after an unchecked `.update()` is the single most dangerous class of silent-failure bug in this codebase** — the UI shows a normal success navigation (contact created, new form prefilled) while the actual state transition (status change, flag flip) silently failed and the row is left stuck in its old state. Found live via this exact pattern in `convertLead`/`convertLeadToDeal`: the contact insert succeeds, the `leads.update({status:'converted', contact_id})` call right before `redirect()` has no `if (error)` guard, so a blocked/failed update leaves the lead `status='new'`, `contact_id=NULL` forever while the agent is already looking at a prefilled "new deal" form. Grep `grep -rn "redirect(" src/features/*/actions/*.actions.ts -B5` for any `.update()`/`.insert()` immediately before a `redirect()` call with no `error` check between them — this is a reusable audit query across the whole actions tree, not a one-off for leads.
10. **The server access-log line itself does not surface a swallowed trigger error to the user.** `POST ... 200` plus a `[db] P0001 <message>` line a few lines earlier in the same log does NOT mean that specific request failed — the trigger error could belong to an earlier unrelated attempt in the same dev session. Always correlate by re-querying the actual row state in the DB (`select status, contact_id from leads where id=...`) right after the UI action, not by scanning nearby log lines for an error string.
11. **Setting a native `<select>`'s `.value` to a string that is not one of its actual `<option value="...">` values silently no-ops** — `selectedIndex` stays 0, the `change` event fires with the unchanged (often empty) value, and any URL/query param built from it is simply absent. Read `[...select.options].map(o=>o.value)` first (not the visible label text) and set `.value` to one of those exact strings before asserting the filter/form behaved wrong — a filter that looks ignored is very often just the wrong value string, not a real app bug.
12. **A `<button type="submit">` inside a React 19 Server Action form (`<form action={serverFn}>`, empty `action=""` attribute) can silently refuse to submit when a `type="number"` field holds a value outside its `min`/`max`** — neither `.click()`, a JS-dispatched click, nor `form.requestSubmit()` triggers a network request, and no error message appears anywhere in the DOM; the only visible symptom is that the access log never gains a new `POST` line. Confirm by setting the same field to a valid value and re-submitting — if that succeeds immediately, the earlier value was the (silent) blocker, not a server-side validation bug worth chasing further.
13. **The browser never fires `submit` on an invalid native form, so `onSubmitCapture`/`onSubmit` handlers never run to recover** — the only hook point is the submit BUTTON's own `onClick`. Fix pattern: on the button's `onClick`, call `form.checkValidity()`; if false, find `form.querySelector(':invalid')`, walk `.closest('details')` and force it open if the invalid field is hidden inside a collapsed `<FormExtra>`/accordion, `scrollIntoView`, then call `form.reportValidity()` to surface the browser's native tooltip on the actual field. Do not rely on `preventDefault` — `checkValidity()===false` already stops the submit; the handler only needs to make the failure visible.
14. **A `safeParse(...).success ? data : {}` fallback on a JSON blob silently discards ALL fields in that blob when even ONE nested field fails validation** — not just the bad field. Reproduce by POSTing a payload with N valid keys plus one deliberately invalid nested value (e.g. `cohabitants[0].full_name=''` against a `.min(1)` schema) directly to the Server Action (bypass the client form so native number-input validation doesn't intercept first); check the saved row afterward — if the whole JSON column is `{}`, this is the bug, not a theoretical risk. Fix: return `{success, data} | {success, error}` instead of silently defaulting, and have the caller abort the whole mutation (don't insert the parent row) with the Zod issue's `path.join('.')` + `message` surfaced to the user.
15. **A Server Action's duplicate-detection predicate and its anti-abuse guard must call the exact same comparison function.** When a "find candidates" query and a "block this merge" check in the same feature independently reimplement name/field similarity, loosening one without the other makes the UI propose a pair that the server then silently rejects on submit (looks like a broken button). Extract the comparison into one named function and call it from both places. Also check for a THIRD copy in the page component that re-filters the server's already-filtered result with its own stale rule — a page-level re-filter after the action already filtered is a sign the two drifted apart over time and the page's copy should be deleted, not kept in sync.
