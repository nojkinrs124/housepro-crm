# HousePro CRM Constitution

Свод обязательных принципов проекта. Spec Kit сверяет с ними каждый план
(`/speckit-plan` → Constitution Check) и каждый анализ (`/speckit-analyze`).
Нарушение принципа — либо переделка плана, либо явная запись в
«Complexity Tracking» с обоснованием.

Источник правил — `CLAUDE.md` в корне проекта; здесь они в форме, пригодной для
машинной проверки. Расхождение между конституцией и `CLAUDE.md` разрешается в
пользу `CLAUDE.md`, а конституция правится следом.

## Core Principles

### I. Граница Server / Client Components (NON-NEGOTIABLE)

Нарушение = Runtime Error в проде, который не ловят ни `tsc`, ни `next build`.

- Файл без `'use client'` не содержит `onClick`/`onChange`/`onSubmit`/`onDrag`,
  `useState`/`useEffect`/`useTransition`. Любая интерактивность — отдельный файл
  с `'use client'` наверху.
- Функцию нельзя передать пропом из Server Component в клиентский: RSC-payload её
  не сериализует. Исключение — Server Action в `action`/`formAction`. Вместо
  колбэка передаётся сериализуемое (строка-шаблон, объект, массив).
- Из файла с `'use client'` серверный код рендерит только PascalCase-компонент как
  JSX. Обычные функции оттуда не импортируются — вызов с сервера падает в рантайме.
  Чистые типы и функции выносятся в файл без `'use client'`.

План, добавляющий интерактивный UI, обязан явно называть, какие файлы клиентские,
а какие серверные.

### II. Схема БД меняется только миграцией

- Изменение схемы — только через `apply_migration`, никогда `execute_sql`
  (заблокировано хуком `guard-sql`).
- `DROP TABLE` / `TRUNCATE` / `DROP COLUMN` запрещены — единственный путь к потере
  боевых данных (заблокировано хуком `guard-migration`). Удаление данных — только
  отдельным осознанным решением человека.
- Каждая новая таблица несёт `organization_id` и RLS-политики с изоляцией через
  `get_user_org_id()`. Таблица без RLS в план не проходит.
- После каждой миграции — регенерация `src/types/supabase.ts`. Руками этот файл
  не правится.
- Актуальный список таблиц берётся через MCP `list_tables`, а не по памяти.

Процедура — skill `housepro-migration`.

### III. Типы вместо `any`

- `any` в новом коде запрещён; честно неизвестный тип — `unknown` с сужением.
- Доменные типы берутся из `@/types/database` (`Row<'deals'>`, `Insert<…>`,
  `Update<…>`), а не переизобретаются как `Record<string, unknown>`.
- Число оставшихся легаси-`any` не растёт: ратчет `npm run check:any` держит
  baseline. Тронул файл — убрал `any` оттуда и переснял baseline.

### IV. Визуальный стандарт «Кабинет»

Проверяется линтером `npm run check:design`, детали — skill `housepro-ui`.

- Цвет только через токены `var(--hp-*)`. Хардкод хекса и палитра Tailwind
  (`bg-blue-500`, `text-slate-600`) запрещены.
- Теней нет; форму карточки задаёт `border border-[var(--hp-border)]`.
- Радиус один и равен 0; `rounded-full` — только точки-статусы, полоски прогресса,
  спиннеры.
- Акцент плоский `var(--hp-accent)`, без градиентов. Hover — только смена цвета
  границы или фона, без `translate`, `scale`, `shadow`.
- Готовые примитивы вместо самодельных: `.hp-input`, `.hp-label`, `.hp-block`,
  `.hp-badge hp-badge-{good|warn|info|danger|neutral}`.
- Сетки только с breakpoint (`grid-cols-1 sm:grid-cols-2`), группы кнопок —
  `flex-wrap shrink-0`.

Новый UI-элемент в плане не изобретается, если такой уже есть в `globals.css`
или `src/components`.

### V. Server Action как единственная точка записи

Мутации идут через Server Action по шаблону из `CLAUDE.md` и в этом порядке:
проверка `auth.getUser()` → `requireOrgId()` → rate limit → `zod`-валидация →
запрос в Supabase → `revalidatePath` → `redirect`. Пропуск любого шага —
дыра в мультиарендности или в защите от перебора, а не «упрощение».

Дубль имени функции в `*.actions.ts` валит сборку Turbopack.

### VI. Зелёная проверка и поднятая версия перед пушем

- `npm run check` (tsc → границы client/server → функции-пропы → правила серверного
  слоя → `any` → визуальный стандарт → кроны → build → тесты) обязан быть зелёным
  на текущем коде. Пуш без этого блокирует хук `guard-bash`.
- Версия в `package.json` поднимается тем же коммитом, что и правки в `src/` или
  `supabase/migrations/`: `npm run version:patch|minor|major`. Версия — из
  `@/lib/version`, руками в разметку не вписывается.
- README обновляется, когда появился новый модуль (напоминает хук `stop-readme`).

Процедура выката — skill `housepro-release`.

### VII. Production-ready, без заглушек

Задача считается сделанной, когда работает целиком: заглушки, «здесь потом
допишем», закомментированные ветки и мёртвые флаги в `main` не попадают. Если
часть объёма выполнить нельзя — это фиксируется явно, а не маскируется пустой
реализацией.

## Технологические ограничения

Стек зафиксирован: Next.js 16 · React 19 · TypeScript · Tailwind v4 (только через
postcss) · Supabase (Postgres + Auth + Storage) · react-hook-form + zod ·
docxtemplater/pizzip · pdf-lib · recharts · sonner · framer-motion · lucide-react ·
Upstash Redis · Stripe · Sentry · vitest + Playwright.

- Новая runtime-зависимость требует обоснования в плане: почему не хватает того,
  что уже есть в стеке.
- Запрещены `axios` (есть `fetch`), `react-query`, вторая библиотека
  drag-and-drop (Kanban — на нативном HTML5 DnD). Блокирует хук `guard-bash`.
- Библиотеки UI-компонентов в проекте нет и не заводится: `src/components/ui/` —
  свои файлы.
- `npm install` — только с `--legacy-peer-deps`.
- Шрифты Source Sans 3 и Source Serif 4 не заменяются: у альтернатив нет кириллицы.
- Кроны Vercel Hobby: частота ограничена, проверяется `npm run check:cron`.

## Рабочий процесс

Порядок для новой функциональности:

1. `/speckit-specify` — что и зачем, на языке пользователя CRM. Без технических
   решений.
2. `/speckit-clarify` — снять неоднозначности до планирования.
3. `/speckit-plan` — техническое решение со сверкой по этой конституции.
4. `/speckit-tasks` — задачи в порядке зависимостей.
5. `/speckit-analyze` — сверка spec / plan / tasks между собой (по желанию).
6. `/speckit-implement` — реализация.
7. Выкат по skill `housepro-release`.

Артефакты живут в `specs/NNN-имя-фичи/` и коммитятся вместе с кодом.

Разделение ответственности между документами:

- конституция — принципы, нарушать которые нельзя;
- `CLAUDE.md` — правила, действующие всегда;
- skills `housepro-*` — процедуры (как именно сделать);
- `.claude/hooks/` — жёсткие запреты, исполняются машиной;
- `docs/IMPROVEMENTS.md` — единственный бэклог;
- `docs/JOURNAL.md` — хроника, не правила.

## Governance

- Конституция главнее привычек и предыдущих решений. Если план ей противоречит —
  меняется план.
- Отступление допустимо только явное: раздел «Complexity Tracking» в `plan.md`
  с указанием, какой принцип нарушен, зачем и что было отвергнуто как более простая
  альтернатива. Молчаливое нарушение — дефект.
- Принципы I–VI дублируются автоматическими проверками (`npm run check`,
  `.claude/hooks/`). Правка принципа, у которого есть проверка, тянет за собой
  правку проверки — иначе конституция расходится с реальностью.
- Изменение конституции: правка этого файла + подъём версии ниже. MAJOR — принцип
  удалён или переопределён несовместимо, MINOR — добавлен принцип или раздел,
  PATCH — уточнение формулировки без смены смысла.
