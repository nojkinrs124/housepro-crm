# Правила для API routes

- **Supabase-клиент** — `getSupabaseAdmin()` лениво **внутри** хендлера, с `no-store`
  fetch-конфигом. Не копировать инстанциацию в очередной файл — выносить общий
  паттерн в `src/lib/`, если он повторяется (сейчас такого общего хелпера нет).
- **GET с данными по организации** — обязательно `export const dynamic = 'force-dynamic'`,
  иначе Next закэширует ответ на билде и все арендаторы получат чужие данные.
  Проверяется хуком на каждую правку (`scripts/checks/server-rules.mjs`).
- **Публичный API `/api/v1`** — авторизация только через `authenticateApiKey()`
  (`src/lib/api-auth.ts`), org берётся из ключа, не из сессии.
- **Вебхуки внутрь** (`/api/telegram`, `/api/signing`, `/api/payments/yookassa`) —
  проверять подпись до любой работы с телом запроса; тело читать как `text()`,
  а не `json()`, иначе подпись не сойдётся.
- **Кроны** (`/api/cron/*`) — сверять `CRON_SECRET`. Расписание в `vercel.json` только
  суточное и реже; чаще — pg_cron в Supabase (миграции
  `20260915080224_pg_cron_frequent_jobs.sql` и
  `20260915080914_pg_cron_secret_selfcontained.sql`), а в роуте — `isCronAuthorized`
  из `src/lib/cron-auth.ts`: он принимает и `CRON_SECRET`, и секрет pg_cron из Vault. GitHub Actions для этого
  не годится: с 27.08.2026 schedule-запуски троттлятся до 2–9 в сутки.
- **Секреты** — предпочтительно через `src/lib/env.ts`. Правило не абсолютное: в
  проекте ~125 прямых обращений к `process.env` в ~55 файлах, и большинство законны
  (провайдеры почты, вебхуки Telegram/signing — читают ключи по месту). В новом коде
  брать из `env.ts`, существующие не переписывать без повода.
