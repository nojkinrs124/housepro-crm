# Упрощение веб-CRM HousePro

Ты приводишь веб-интерфейс CRM к состоянию, в котором **новый сотрудник без объяснений выполняет рабочую задачу с первого раза**.

Целевой пользователь — не разработчик и не владелец системы, а нанятый агент, впервые открывший CRM. Всё, что требует объяснений, догадок или знания истории проекта, — дефект.

Аргумент команды: $ARGUMENTS
Если аргумент пустой — работаешь по всем модулям. Если указан модуль — только по нему, но фазы 0 и 1 всё равно выполняются (в сокращённом объёме).

## ГЛАВНОЕ ПРАВИЛО ПРОГОНА: всё локально

Вся работа идёт на локальной машине. **Ни одного `git push` до явного финального подтверждения владельца.**

- Коммиты делаешь — они локальные, нужны для отката между волнами.
- Пуш не делаешь никогда, ни после волны, ни после фазы, ни «чтобы не потерять».
- Ветка `simplify/ux` существует только локально.
- Проверка — локальная production-сборка, а не превью Vercel.
- Правило проекта «коммит + пуш после каждой фазы» на этот прогон **отменено владельцем**. Действует: коммит — да, пуш — нет.

Пуш происходит ровно один раз, в самом конце, после того как владелец увидел итоговый отчёт и сказал пушить.

## Жёсткие границы — НЕ ТРОГАТЬ

Эти зоны не меняются ни при каких обстоятельствах:

- **Telegram-бот и ассистент канала** — весь код бота, меню, рубрики, расписание, генерация картинок.
- **Публичное API `/api/v1/`** — контракты могут быть завязаны на внешние интеграции.
- **Генерация документов** (`docxtemplater`, шаблоны DOCX, `document.service.ts`) — юридически значимый поток.
- **Схема БД** — кроме удаления объектов, доказанно мёртвых по критериям фазы 1.
- **Логика прав** (`requirePermission`, `permissions.ts`) — можно добавлять роли для сокрытия функций, но нельзя ослаблять существующие проверки.
- **Денежные потоки** (`accounting_transactions`, платежи по договорам) — UI можно упрощать, бизнес-логику расчётов нельзя.

Если для выполнения задачи нужно зайти в запретную зону — не заходи, зафиксируй это в отчёте на гейте.

## Правила простоты (критерий приёмки каждого экрана)

Это измеримые правила. Экран считается готовым, только если проходит все:

1. **≤ 3 кликов** от главной страницы до завершения любого частого действия.
2. **Одна главная кнопка на экран.** Ровно одна кнопка — визуально первичная. Остальные — вторичные или в меню «…».
3. **≤ 6 полей в форме по умолчанию.** Всё остальное — свёрнуто в «Дополнительно». Обязательных полей — минимум, остальные можно заполнить позже.
4. **Единый скелет модуля:** список → фильтр → карточка → действия. Никаких уникальных структур «только у этого модуля».
5. **Нет пустых экранов.** Если данных нет — текст «что это такое и что тут делать» плюс кнопка, которая это делает.
6. **Человеческий язык.** Никаких `deal_stage`, `contact_role`, `null`, кодов ошибок и англицизмов в интерфейсе. Ошибка говорит, что произошло и что сделать дальше.
7. **Необратимое действие подтверждается, обратимое — нет.** Удаление спрашивает. Сохранение — не спрашивает, просто сохраняет и показывает toast.
8. **Одно действие — один способ.** Если создать сделку можно тремя разными путями, оставь один и убери остальные.

## Политика удаления

Действует строго:

- **Удаляем** только доказанно мёртвое. Доказательство = нет импортов + нет вызовов + нет роута + (для таблиц) нет строк или нет обращений в коде. Проверка через `grep` по всему репозиторию, а не «на вид не используется».
- **Прячем, а не удаляем** всё живое, но редкое: убираем за роль, во вкладку «Ещё» или в «Дополнительно». Код остаётся на месте.
- **Не удаляем никогда** ничего из запретных зон выше.
- Всё скрытое записывается в `docs/HIDDEN.md` с датой и причиной — через 2–3 недели по этому списку пройдёт второй проход на удаление.

## ФАЗА 0. Страховочная сетка

1. Создай ветку `simplify/ux` от актуального `main`. Всю работу ведёшь в ней, `main` не трогаешь до самого конца.
2. Разберись с текущим состоянием тестов: конфиг Playwright, существующие спеки в `e2e/`, доступы в `.env.e2e`, против какого окружения они ходят. Ничего не спрашивай — посмотри сам в репозитории и в CI.
3. **Подними изолированное окружение Supabase.** Смоук не должен писать в боевую базу — договоры и платежи это юридически и денежно значимые записи.

   **Основной путь — локальный Supabase.** `npx supabase start` поднимает стек в Docker, `npx supabase db reset` накатывает миграции из репозитория. Бесплатно, полностью локально, прод недосягаем физически. Если Docker не установлен или стек не стартует — разберись сам, это разовая настройка.

   **Запасной путь — dev-ветка в облаке**, только если локальный стек поднять не удалось. Через Supabase MCP: `get_cost` → `confirm_cost` → `create_branch`. Требует тарифа Pro и включённого branching; если откажет — **остановись и вынеси на гейт**.

   **Прод — никогда**, ни при каком отказе обоих путей. Нет изоляции — нет тестов и нет рефакторинга.

   Дальше в обоих случаях:
   - заведи `.env.e2e.branch` с URL и ключами изолированного окружения. **Файлы `.env.local` и `.env.e2e` не трогай** — они боевые;
   - напиши идемпотентный seed-скрипт `e2e/seed.ts`: организация и админ-пользователь, профиль компании, справочники и стадии, шаблоны DOCX в Storage. Состав выясняй не по догадке, а прогоном: запустил тест, посмотрел, на чём упал, дополнил seed.
4. Напиши смоук-тесты на 7 критичных потоков:
   - вход и выход из системы;
   - создание контакта;
   - создание сделки;
   - перетаскивание сделки по канбану между стадиями;
   - создание задачи;
   - генерация договора;
   - проведение платежа по договору.

   Тесты проверяют **факт выполнения операции и попадание данных в БД**, а не вёрстку. Они должны пережить перекройку интерфейса — цепляйся за `data-testid`, а не за текст кнопок и структуру DOM. Где `data-testid` нет — добавь.
5. **Прибей тесты к изолированному окружению намертво.**
   - отдельный скрипт запуска, читающий `.env.e2e.branch`, — не переиспользуй существующую команду, которая смотрит в боевое окружение;
   - в `globalSetup` сравни URL Supabase с боевым (`zwclvcswvhjeqwxrkbte`) и **брось ошибку**, если они совпали. Это предохранитель от случайного прогона по проду, он важнее самих тестов;
   - записи всё равно создавай с префиксом `__smoke__` и подчищай в `afterAll`.
6. Прогони тесты на текущем коде. Все должны быть зелёными до начала рефакторинга. Если какой-то поток сломан уже сейчас — не чини молча, вынеси на гейт.
7. Локальный коммит: тесты, seed, конфиг. **Не пушить.** Убедись, что `.env.e2e.branch` попал в `.gitignore` и не коммитится.

Если смоук-тесты невозможно запустить — остановись и вынеси проблему на гейт **до** начала аудита. Рефакторинг без сетки не начинаем, обходных путей через прод не ищем.

## ФАЗА 1. Параллельный аудит

Запусти **одним сообщением пять субагентов через Task, параллельно**. Все пятеро работают только на чтение.

| Агент | Что ищет |
|---|---|
| `ux-flow-auditor` | Длинные и тупиковые сценарии, лишние шаги, клики |
| `ui-consistency-auditor` | Расхождения в паттернах списков, форм, кнопок, модалок |
| `dead-code-hunter` | Неиспользуемый код, компоненты, роуты, экшены, зависимости |
| `db-junk-auditor` | Пустые таблицы, мёртвые колонки, неиспользуемые функции и индексы |
| `copy-auditor` | Технические термины в интерфейсе, плохие ошибки, отсутствующие подсказки |

Каждый возвращает структурированный отчёт по формату из своего описания.

Ты собираешь из пяти отчётов **один документ** `docs/SIMPLIFY-AUDIT.md` с тремя списками:

- **A. Мёртвое — сношу сам.** Каждая позиция с доказательством (результат grep, число строк в таблице).
- **B. Спорное — нужно решение владельца.** Каждая позиция с вариантами: удалить / скрыть / оставить. **Рекомендация по умолчанию для этого списка — «скрыть».**
- **C. Изменения UI/UX.** Сгруппированы по модулям, каждая позиция ссылается на конкретное правило простоты, которое она чинит.

Документ должен читаться за 10 минут. Не пересказывай код — пиши, что не так и что предлагаешь.

## ФАЗА 2. ГЕЙТ — ЕДИНСТВЕННАЯ ОСТАНОВКА

Покажи владельцу документ и **остановись**. Не начинай ничего править, пока не получишь явное подтверждение по списку B.

Это единственное место во всём прогоне, где ты задаёшь вопросы. До гейта и после гейта — работаешь автономно, без запросов подтверждения между шагами.

## ФАЗА 3. Эталонный модуль

Модуль-эталон — **Сделки**.

1. Приведи его в полное соответствие всем восьми правилам простоты.
2. Вынеси получившиеся паттерны в переиспользуемые компоненты (скелет списка, скелет карточки, скелет формы, пустое состояние, панель действий).
3. Допиши в `CLAUDE.md` раздел «Правила интерфейса CRM»: восемь правил + названия эталонных компонентов + указание, что все новые экраны строятся только из них.
4. `npm run check` → смоук → локальный коммит. **Не пушить.**
5. Подними локально production-сборку (`npm run build && npm start`), убедись сам, что модуль работает, и напиши владельцу одним сообщением: что изменилось в «Сделках» и как это посмотреть локально. Продолжай работу, не дожидаясь ответа — если он остановит, откатимся на один коммит.

## ФАЗА 4. Тираж по волнам

Порядок волн, менять только по прямому указанию:

1. Контакты
2. Задачи
3. Объекты
4. Договоры
5. Бухгалтерия
6. Лиды
7. Показы, Подборки, Файлы
8. Аналитика, Сотрудники, Настройки компании
9. Навигация, глобальный поиск, уведомления, онбординг

**Одна волна = один модуль.** Правишь строго по одному, параллельных правок нет — субагенты на этом этапе не используются.

Цикл каждой волны, без исключений:

1. Привести модуль к эталону по восьми правилам.
2. Применить решения из списков A и B по этому модулю.
3. `npm run check` на существующем окружении. Файлы `.env*` не создавать, не править и не удалять.
4. Прогнать смоук-тесты против изолированного окружения.
5. **Красный шаг блокирует всё.** Чини до зелёного. Не переходи к следующей волне со сломанным тестом и не отключай тест, чтобы он стал зелёным.
6. Локальный коммит, отдельный на каждую волну, с понятным сообщением. **Не пушить.**

Если волна потребовала изменений в общих компонентах — после неё обязательно прогони смоук целиком, а не только по текущему модулю.

Отдельные коммиты на волну — это твоя кнопка отката. Не сваливай несколько модулей в один коммит.

## ФАЗА 5. Полная локальная регрессия

Здесь проверяется всё и сразу, на чистую голову.

1. Прогони `npm run check` целиком.
2. Прогони **весь** смоук, а не выборочно.
3. Собери production-сборку локально (`npm run build && npm start`) и пройди руками по всем девяти сценариям из фазы 0 в собранном приложении, а не в dev-режиме. Dev скрывает часть ошибок сборки и гидрации.
4. Проверь консоль браузера и логи сервера на ошибки и предупреждения. Любая новая ошибка в консоли — дефект, чинится здесь же.
5. Пройди по всем модулям с чек-листом из восьми правил простоты и зафиксируй, какие экраны его не проходят и почему.
6. Составь `docs/SIMPLIFY-REPORT.md`: что сделано, что скрыто (со ссылкой на `docs/HIDDEN.md`), что удалено, что осталось недоделанным, сколько кликов было и стало на трёх главных сценариях, результаты всех прогонов.
7. Убедись, что рабочая директория чистая: временные файлы, логи тестов и `.env.e2e.branch` не попали в коммиты, боевые `.env.local` и `.env.e2e` не изменены.
8. Покажи владельцу отчёт и **остановись**. Если использовалась облачная dev-ветка — отдельной строкой напомни, что она тарифицируется и после мержа её нужно удалить. Сам не удаляй.

## ФАЗА 6. Передача владельцу

**Ты не пушишь. Никогда, ни на этой фазе, ни на какой другой.** Пуш делает владелец руками.

Твоя работа здесь заканчивается одним сообщением:

1. Ветка `simplify/ux` готова, N коммитов, все локальные.
2. Результаты финальной регрессии: `npm run check`, смоук, ручной проход.
3. Что смотреть в первую очередь при ревью.
4. Что удалено, что скрыто, что осталось недоделанным.
5. Напоминание удалить облачную dev-ветку Supabase после мержа, если она использовалась.

Дальше останавливаешься. Не предлагай запушить, не спрашивай, когда пушить, не напоминай. Работа может пролежать локально сколько угодно — это нормальное состояние.

## Технические правила прогона

- `npm install` только с `--legacy-peer-deps`.
- Обработчики событий (`onClick`, `onChange`, `onSubmit`, `onDrag`) — только в компонентах с `'use client'`. Никогда в серверных.
- Формы — только по канону `ServerActionForm.tsx`.
- Перед добавлением функции в файл экшенов — `grep`, чтобы не создать дубликат.
- Таблицы `clients` и `owners` — легаси, новый код на них не завязывается.
- Изменения схемы БД — только через `apply_migration`, файл миграции сразу коммитится.
- Не заводи командную обвязку (CODEOWNERS, шаблоны PR, husky, lint-staged) — в проекте один разработчик.
- Файлы `.env.local` и `.env.e2e` — боевые. Не создавать, не перезаписывать, не удалять, не читать значения в вывод. Единственный файл окружения, который ты заводишь, — `.env.e2e.branch`, и он в `.gitignore`.
- Токены и PAT не трогаешь вообще: не запрашиваешь, не подставляешь в команды, не выводишь. Хук `guard-bash` их блокирует, и это правильно.
- Всё выполняется локально. Пуш не входит в твои обязанности ни на одной фазе.

## Чего делать нельзя

- **Делать `git push`.** Ни разу, ни на одной фазе, ни по просьбе, ни «чтобы не потерять». Пушит владелец.
- **Запускать смоук против боевого Supabase.** Только локальный стек или облачная dev-ветка. Нет изоляции — нет тестов и нет рефакторинга.
- Создавать, править или удалять `.env.local` и `.env.e2e`.
- Начинать правки до зелёного гейта.
- Удалять живой код «на всякий случай» — только прятать.
- Отключать, пропускать или ослаблять тест, чтобы прогон стал зелёным.
- Переходить к следующей волне при красном `npm run check` или смоуке.
- Задавать вопросы вне гейта — везде, кроме фазы 2, действуй сам.
