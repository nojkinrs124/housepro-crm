# /walkthrough — сквозной проход по CRM

Аргументы: `$ARGUMENTS`
- пусто или `all` — все сценарии;
- список кодов через пробел (`L RA TS`) — только они;
- `report` — не проходить, только собрать отчёт из `docs/qa/.walkthrough/*.md`;
- `prod` — режим только-чтение на боевом сайте (см. §4).

Сценарии, порядок и инварианты — в **`docs/qa/WALKTHROUGH.md`**. Прочитай его
целиком один раз, прежде чем что-либо запускать. Исполнитель — агент
`crm-walkthrough`.

## Главные правила

1. **Молча.** Владелец не хочет отчёт по каждому действию. В чат — три
   сообщения за весь прогон: «окружение поднято, запускаю N сценариев»,
   при необходимости «блокер, требуется решение» и **итог**. Всё остальное —
   в файлы.
2. **Только локально.** База — Docker-стек, CRM — `http://localhost:3100`.
   Если `.env.e2e.branch` содержит `zwclvcswvhjeqwxrkbte` или `supabase.co` —
   стоп. `.env.local` / `.env.e2e` не открывать.
3. **Ничего не чинить.** Проход — наблюдение. Исправления — отдельный шаг
   после итога, по решению владельца.
4. **Не спрашивать** по ходу. Единственное исключение — Блокер, который
   останавливает больше половины оставшихся сценариев и не имеет обхода.

## 1. Окружение

```bash
npm run walkthrough:up
```

Запускай **в фоне** (`run_in_background: true`, таймаут 600000): скрипт
поднимает Supabase, пишет `.env.e2e.branch`, сидит фикстуру, собирает
production в `.next-walk` и держит сервер на `:3100`. Готовность — строка
`→ production-сервер: http://localhost:3100` в выводе; дождись её через
`Monitor` или чтение файла вывода, не опрашивай в цикле.

Если порт занят — `WALK_PORT=3101 npm run walkthrough:up` и дальше везде 3101.

Затем:
- `rm -rf docs/qa/.walkthrough && mkdir -p docs/qa/.walkthrough`;
- открой браузер: `preview_start {url: "http://localhost:3100/login"}`;
- войди фикстурой (`E2E_TEST_EMAIL` / `E2E_TEST_PASSWORD` из
  `.env.e2e.branch` — локальная тестовая учётка, вводить её можно);
- убедись, что `/dashboard` открылся.

## 2. Запуск сценариев

Сценарии зависят друг от друга по данным, поэтому три волны. Каждый агент —
`Agent {subagent_type: "crm-walkthrough", run_in_background: true}`, в задании:
`scenario`, `baseUrl`, `tabId`, `outFile`, `fixtures` (см. промпт агента).
`fixtures` — блок «Созданные записи» из файлов предыдущих волн, скопированный
как есть.

| Волна | Сценарии | Как |
|---|---|---|
| 1 | `NAV`, `SET`, `L`, `CP` | **последовательно** в одной вкладке — они создают фундамент (тарифы, контакты, объекты) |
| 2 | `RA`, `MG`, `SL`, `TS` | **параллельно**, каждому своя вкладка (`tabs_create` → `tabId`); каждый создаёт свои сделки по своим контактам/объектам из `fixtures` |
| 3 | `CT`, `AC`, `SHTK`, `AN`, `DB` | `CT`/`AC`/`SHTK` параллельно, затем `AN` и `DB` последовательно — они сверяют итоги |

Если агент отвечает, что браузерные инструменты ему недоступны, — выполняй
сценарии сам, в том же режиме (без промежуточных сообщений, всё в файлы),
по одному, в порядке волн.

Ожидание агентов — через уведомления о завершении, не через опрос. Пока ждёшь,
ничего не пиши в чат.

## 3. Итог

Когда все файлы `docs/qa/.walkthrough/*.md` на месте:

1. Собери `docs/qa/WALKTHROUGH-REPORT-<ГГГГ-ММ-ДД>.md` по §15
   `WALKTHROUGH.md`: шапка, сводка по классам, таблица дефектов (Блокер →
   Логика → Разрыв → UX → Текст, внутри класса — по ID шага), «Обойдённые
   предусловия», «Что работает», «Вопросы владельцу».
2. Дедупликация: один и тот же дефект, найденный в `RA` и `MG`, — одна строка
   с двумя ID.
3. Добавь раздел **«Рекомендации»**: 5–10 пунктов, каждый — что исправить,
   почему это важно риелтору, какие ID закрывает, оценка объёма (S/M/L) и
   риск (трогает ли деньги/договоры/права). Порядок — по влиянию на
   ежедневную работу, не по простоте.
4. Опубликуй отчёт как Artifact (владелец читает с телефона).
5. **Одно сообщение в чат**: сколько сценариев пройдено/пропущено, сколько
   дефектов по классам, топ-5 находок в одну строку каждая, ссылка на
   Artifact и путь к файлу, и вопрос: «Чинить по списку рекомендаций?».

Ничего не коммить: отчёт и `.walkthrough/` — рабочие файлы, владелец решит.
Сервер и Supabase не останавливай — владелец может захотеть посмотреть сам;
скажи в итоге, что остановить можно `npm run walkthrough:down`.

## 4. Режим `prod` — только чтение

Для сверки с реальными данными. Правила жёстче:
- открыть `https://housepro24.vercel.app/login` и **попросить владельца войти
  самому** в панели браузера; учётки не вводить;
- агентам передать `readOnly: true`; они только открывают страницы и читают
  (`read_page`, `get_page_text`), **ни одной формы, ни одной кнопки действия,
  ни одного перетаскивания**;
- сценарии — только `NAV`, `AN` и «прочитать карточки существующих лидов и
  сделок по каждому направлению»; всё, что создаёт данные, — пропуск;
- в отчёте отдельный раздел «Прод: что видно на реальных данных».
